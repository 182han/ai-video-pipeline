## 1. 定位变更：从「展示型网页」到「工具/软件」

这一节是**可判定条款**，不是口号。UI 的每一屏都可以拿这 6 条来判「这屏是工具还是网页」。

**G1｜操作反馈时限**
任何点击类操作，**在 200 ms 内必须出现可见状态变化**（按钮进入 loading、行内出现进度、或即时提示）。
禁止「点了没反应，几秒后突然跳转」。
> 判定：录屏逐帧看首帧反馈时间。超过 200 ms 即不通过。

**G2｜不做装饰性动画**
工作台区域（任务、参数、审核、资产）**不允许**入场动画、滚动视差、粒子/光晕/玻璃拟态。
允许动画的只有两处：进度数值变化（≤300 ms 过渡）、成片预览区的播放器本身。
> 理由：产品核心是「判断画面」。任何额外视觉信息都会干扰对色彩和画质的判断（与 UI 任务书的硬性约束一致）。

**G3｜不让用户靠猜**
每个耗时步骤必须显示：**当前步骤名 / 第几步 / 已用时 / 预计剩余或"未知"**。
「预计未知」允许显示为「预计：未知」，**不允许用假进度条填满**（`AGENTS.md` §4.8 不许谎报状态）。
> 映射：步骤名与顺序来自 `app/src/taskManager.js:26` 的 `PIPELINE_STEPS`；进度取 `GET /api/tasks/:id/progress`（`app/server.js:1272`）。

**G4｜不隐藏付费动作**
任何会触发模型 API 计费的动作（生成、重新生成、重检）在点击前必须能看到**将发生几次调用**。
> 映射：`app/src/pricing.js`（已存在计费估算）；片段级再生成见 `POST /api/tasks/:id/clips/:index/regenerate`（`app/server.js:1566`）。

**G5｜空状态给下一步动作**
每个空列表（任务为空、片段库为空、待审为空）必须给**一个可点的主行动**，不放插画占位。

**G6｜成片预览区是唯一的展示化区域**
暗场、播放器质感、全屏、无干扰——这块按 UI 任务书做展示化处理；其余区域按工具标准。
> 映射：成片列表 `GET /api/tasks/completed`（`app/server.js:374`）、`app/public/showcase.html`。

## 3. 新工作流 W1–W10

> 每一步固定写 4 项：**输入 / 输出 / 失败后果 / 代码映射**。
> 「失败后果」区分两种：**可继续**（该点失败不阻塞下游，但必须显式标注）与 **阻塞**（必须停下等人决策）。

### W1｜提示词（用户输入 + 优化）
- **输入**：用户一句话创意或逐行多段提示词、主题、单段时长、片段数、模型、分辨率档（`resolution`）。
  > **现状限定**：代码与前端**都没有「画幅 / aspectRatio」概念**【实测】——
  > `grep aspectRatio` 在 `app/src/taskManager.js` 与 `app/public/index.html` 均无命中，
  > 只有 `resolution`（480p/720p/1080p/4K，`taskManager.js:238`）。
  > 屏保播放（Android TV）实际是横向 16:9，但这是**隐含假设**，不是字段。
  > 因此 W3 的「图片比例必须匹配视频」在现状里**无依据可用**，见 Q8。
- **输出**：`task.prompt` / `task.prompts[]`、经模板结构化的 `optimizedPrompt`、每个片段的场景提示词。
- **失败后果**：**可继续**。LLM 不可用时降级为模板分镜，但必须在任务上留痕（现状已有降级标记逻辑，见映射）。
- **映射**：创建任务 `POST /api/tasks`（`app/server.js:1103`，字段解构 `:1104`）；多提示词校验 `:1109-1110`；
  优化器 `src/promptOptimizer.js`（`module.exports` 在 `:886`）；步骤实现在 `pipeline.js:1072`；
  多段提示词分流 `:1076`。
- **需求**：
  - **W1-a** 用户必须能**同时看到**「我输入的」与「优化后的」两份提示词，并可只采用其一。
  - **W1-b** 逐行多段模式（`prompts[]`）必须保留，且**分镜步骤不得覆盖用户逐行场景**（现状已如此，`pipeline.js:1134-1137`：多提示词模式跳过 LLM 分镜）。
  - **W1-c** 提示词模板库（`/api/templates`）与通用优化规则（`/api/rules`）在此步可调用。

### W2｜分镜
- **输入**：`task.prompt`（单段模式）或 `task.prompts[]`（多段模式）、`totalClips`。
- **输出**：`task.clips[i].prompt` —— 每个片段一条**差异化**场景提示词（LLM 负责内容差异，模板负责结构）。
- **失败后果**：**可继续**。LLM 无 Key 或调用失败 → 沿用模板分镜，标记 `degraded` 与原因，**不报错不阻塞**。
- **映射**：`pipeline.js:1130`（步骤开始）→ `:1142` `llmService.storyboard(...)` → `:1151` `updateClip(prompt)`
  → `:1163` `qualityChecker.checkStoryboard` → `:1170` 记录完成。降级处理 `:1154-1158`、`:1164-1168`。
- **需求**：
  - **W2-a** 分镜结果必须**可编辑**（逐条改文案），因为 W3 的图片直接用这条文案生成。
  - **W2-b** 分镜数量必须等于 `totalClips`；不一致时按现状补/截，但要显示提示（见 `checkStoryboard` 的入参 `totalClips`）。
  - **W2-c** 降级必须显式可见（「本次分镜为模板生成，非 LLM」），不得静默。

### W3｜图片生成（**新增**）
- **输入**：`clips[i].prompt`、主题、目标分辨率档、`IMAGE_GEN_*` 配置。
- **输出**：每段一张静帧，落盘路径 + 元数据（provider / model / 尺寸 / 耗时），供 W4 审。
- **失败后果**：**部分失败可继续**（单张失败不拖死整组，但整组全失败 = 阻塞）。
- **映射（0 起点）**：`src/generators/imageGen.js`（`generateImage` 目前抛错 `:104`）；配置段见 `config.js` 工作区改动；
  阶段需新增到 `pipelineStages.js`（该文件 `:18` 已写明接入点：「在 pipelineStages 增加 image_generation 阶段」）。
- **需求**：
  - **W3-a** 一次任务生成 **N 张**（N = `totalClips`），**逐张可追踪状态**（排队 / 生成中 / 成功 / 失败 / 已通过 / 已驳回）。
  - **W3-b** 单张失败**不得阻塞**其它张的生成，但必须：① 该位置显示失败与原因；② 提供「只重做这一张」；
    ③ 整组进入审核前，**失败位必须显式提醒**「第 3 张未生成，无法通过整组」。
  - **W3-c** 图片**不覆盖**：同一位置第 K 次重做保留旧文件（沿用 `AGENTS.md` §6「重新生成不覆盖已有片段」的既定原则，
    现有实现见 `pipeline._nextClipPath()` 的 `_vK` 后缀语义）。
  - **W3-d** 图片生成**必须能识别合成/Mock 结果**并显著标注，禁止把合成图当真实分镜让人去审
    （依据：`AGENTS.md` §6「真实模型缺 Key 降级 Mock 会被识别」，现有 `task.mockFallback` 机制，`pipeline.js:1195` `_markMockFallback`）。
  - **W3-e** 分辨率/画幅必须与 W5 视频生成所需的首帧规格对齐，**不能出现「图 1024×1024、视频要 16:9」这种要用户自己算的情况**。对齐规则见 §9 Q8。

### W4｜人工审核门（**新增，本规格的核心**）
- **输入**：W3 产出的 N 张图 + 各自对应的提示词。
- **输出**：一组「已通过」的图（或部分驳回后的重做结果），解锁 W5。
- **失败后果**：**阻塞**。审核未通过 = 流水线停在这里，**没有自动放行**。
- **详细规则见 §4（R1–R12）。**
- **映射（0 起点）**：无任何现成路由/状态。最近的相似语义是 `paused`（`pipeline.js:1647-1672`）+ `/api/tasks/:id/pause|unpause|pause-state`（`app/server.js:1540/1546/1553`），但语义不同（见 §2.2）。

### W5｜视频生成（图生视频）
- **输入**：W4 通过的每张图（作为首帧/参考图）+ 该片段提示词（作为运动描述）+ 目标模型。
- **输出**：`clips[i].videoPath`（与现状 `clip_generation` 的产物一致）。
- **失败后果**：**部分失败可继续**，沿用现状 `partial` 语义（`pipeline.js:1226-1229`、`:1622-1640`：部分片段失败仍出成片，任务标 `partial`）。
- **映射**：`pipeline.js:1181-1183`（步骤开始）→ `:1194` `createGenerator` → `:1195` `_markMockFallback` → `_batchGenerate`；
  模型能力来自 `GET /api/models`（`app/server.js:477`），`supportsImageInput` 字段见 `src/generators/index.js`（工作区改动）。
- **需求**：
  - **W5-a 禁止静默降级**：若所选模型 `supportsImageInput !== true`，**不许**悄悄退回纯文生视频把流程跑完——
    那样人工审核门就白设了。必须停下并明说「该模型未核实支持图生视频，请换模型或显式选择『文生视频（跳过图片）』」。
  - **W5-b** 「跳过图片直通文生视频」只能是用户**显式勾选**的一个选项（应急/省钱路径），默认关闭。见 §9 Q6。
  - **W5-c** 视频产物与图片必须可互查：从成片能回到「它用的哪张图、哪条提示词」。

### W6｜拼接
- **输入**：成功的片段列表（按 `index` 顺序）。
- **输出**：`_concat.mp4`（单片段任务例外，见映射）。
- **失败后果**：**阻塞**（没有拼接产物就没有成片）。
- **映射**：`pipeline.js:1293-1295`（步骤开始与状态 `concatenating`）；单片段分支 `:1256-1259`；
  时长校验 `videoProcessor._validateConcatDuration()`（`AGENTS.md` §4.3 要求，退出码 0 不算成功）。
- **需求**：**W6-a** 拼接失败必须给出**人话原因**，不允许只抛 ffmpeg 原始日志；原始日志折叠展示。

### W7｜无缝循环
- **输入**：拼接产物 + `LOOP_FADE_DURATION`（默认 0.5s）。
- **输出**：首尾交叉淡化后的成片母版。
- **失败后果**：**阻塞**（现状已明确「循环失败不回退直通」，见 `AGENTS.md` §6「重建母版路径补齐循环」）。
- **映射**：`pipeline.js:1458-1460`（状态 `looping`）；实现 `videoProcessor._makeLoopFFmpeg`；质检 `qualityChecker.checkLoop`（阈值 `QC_LOOP_SSIM_THRESHOLD` 默认 0.9）。
- **需求**：**W7-a** 循环质检结果必须**展示实测 SSIM 数值**，不能只显示「通过」（`AGENTS.md` §5.1 第 1 条）。

### W8｜配乐
- **输入**：无声母版 `masterPath` + `task.bgm`（模式 auto/manual/off、轨道勾选、音量、淡入淡出）。
- **输出**：`bgmResult`（是否应用成功、段数、错误原因）。
- **失败后果**：**可继续但必须标注**——成片仍然可交付（无配乐），任务不能因此判失败。
- **映射**：`pipeline.js:1558-1560`（步骤 6.5，状态 `mixing`）；配置见 `taskManager.js:165-195`；
  自动配乐计划 `src/processors/bgmPlan.js`；混音 `src/processors/audioMixer.js`；
  接口 `POST /api/tasks/:id/bgm-plan`（`:412`）、`bgm-auto-plan`（`:422`）、`bgm-preview`（`:435`）、`audio`（`:452`）。
- **需求**：**W8-a** 「配乐未应用」必须显式提示原因，不能静默出一版无配乐成片就结束（现有 `bgmResult.ok` 语义已在用，见 `index.html:6455`「已配乐」）。

### W9｜转码
- **输入**：母版。
- **输出**：可交付成片（分辨率/码率/容器符合屏保播放要求）。
- **失败后果**：**阻塞**。
- **映射**：`pipeline.js:1517-1519`（状态 `transcoding`）；`:1537` 写 `masterPath`；质检 `checkTranscode`。
- **需求**：**W9-a** 转码完成必须显示**实测四项**：容器时长、分辨率、帧率、是否存在音轨（`AGENTS.md` §5.2 命令模板）。

### W10｜终检
- **输入**：最终成片路径 + `_finalQcOptions(task)` 运行时配置。
- **输出**：`finalQC` 结论（11 项质检项，含 NSFW）。
- **失败后果**：**阻塞交付**（可以出文件，但不能标「通过」）。
- **映射**：`pipeline.js:1607-1608`；配置组装 `:961-974` `_finalQcOptions`；质检项 `qualityChecker.js:15` `QC_ITEMS`（11 项）；接口 `GET /api/qc-items`（`app/server.js:1216`）。
- **需求**：**W10-a** 质检结论必须严格三态（通过/不通过/未执行），**未执行不得显示为通过**（`AGENTS.md` §4.1）；**W10-b** 每项要给实测数值或「未执行」原因。

### 3.1 执行顺序的一处**冲突**（必须解决，不能含糊）

需求文字写的是「… 配乐 → 转码 → 终检」，但**代码里的实际执行顺序是「转码 → 配乐 → 终检」**：
- `pipeline.js:1517` 转码 → `:1558` 配乐混音（步骤 6.5）→ `:1607` 终检；
- 依赖表明确写着 `audio_mix: ['transcoding']`（`pipelineStages.js:50`），注释（`:37-40`）解释：
  配乐读的是转码产出的**无声母版** `masterPath`，不是拼接产物。

**产品口径（默认决策）**：
1. **执行顺序以代码为准：转码 → 配乐 → 终检。** 需求文字里的「配乐→转码」应理解为「配乐与转码同属后段」，
   不是执行序。
2. **但 UI 上给用户的步骤条可以按用户心智排**（配乐在转码前更符合「先想音乐再导出」的直觉），
   **前提是步骤状态必须真实反映执行**，不能出现「步骤条显示配乐已完成、其实转码还没开始」。
3. 若研发认为必须让执行顺序等于文案顺序，则需先证明配乐可直接读拼接产物而不依赖母版 —— 这需要数据流验证。

→ 编号 **Q2**（卡点：`pipelineStages.js:50` 的依赖关系 vs 需求文案顺序）。
→ 相关问题 **Q3**：`pipelineStages.ALL_STAGES`（`:25-31`）把 `audio_mix` 排在 `transcoding` **之前**，
  而依赖声明 `audio_mix` 依赖 `transcoding`，两者自相矛盾。`resolveStages()` 按 `ALL_STAGES` 排序（`:197`），
  于是 `GET /api/tasks/:id/continue-plan`（`app/server.js:1621`）返回的 `stages`/`pending` 数组顺序
  会把「配乐」排在「转码」前面。**如果 UI 直接按这个数组渲染「将补跑」清单，就会给用户一个与真实执行相反的承诺。**

## 4. 人工审核门规则 R1–R12

### 4.0 先说清「不是什么东西」

用户已确认：**审核由本人完成，单人操作、无审批流、无角色权限**。因此以下东西**一律不做**（不是「暂缓」，是「明确不做」）：

- 没有「审核人 / 指派人 / 会签 / 抄送」字段；
- 没有「通过 → 上级通过」的二级审批；
- 没有「审核意见必填」的表单（允许写备注，但不强制、不做留痕合规要求）；
- 没有角色权限区分（现有 `members.html` 与 `/api/users` 就是**账号平权**，`AGENTS.md` §2.7 已写明「无管理员/普通成员分级」）。

**R1｜单人语义**
审核动作绑定「当前登录账号」，但**不做归属与转交**。任何能登录的人都能审（因为本来只有一个人）。
> 映射：登录墙 `app/src/auth.js`、`/api/auth/*`（`app/server.js:105-163`）。

**R2｜门的位置是固定的，不可跳过**
默认流程里 **W4 必须存在**：`clips[i]` 的图片未经「通过」不得进入 W5。
> 例外只有一条：用户**显式勾选**「跳过图片，走纯文生视频」（W5-b），此时该任务记为**未经过审核门**并打标，
> 便于日后回看时知道「这条成片没人看过图」。见 Q6。

**R3｜默认整组确认，允许逐张覆盖（**这是 R3 的核心决策**）**
一次任务 N 张图（典型 N=10），审核界面默认给 **「整组通过并继续」** 一个主按钮，**不要求逐张点**。
理由：单人操作，逐张点 10 次是纯粹的摩擦；且图片是同一提示词体系的产物，整组质量通常同向。
**但「逐张」必须可用**：每张图有独立的「重做这一张」与「这张不行」。
> 判定：一次 10 张的任务，从进入审核到继续，**最少点击 = 1 次**（整组通过）。这条能否成立直接决定这个工具是「能用」还是「折磨」。

**R4｜整组里有坏图时的行为**
若用户用「整组通过」，但存在 **W3 失败位**（某张没生成出来），则**不许整组通过**，
必须先把失败位处理掉（重做或删除该段并减少总量）。理由：不能让「缺一张」悄悄变成「成片少一段」——
这正是 `AGENTS.md` §6「片段缺失不再静默通过」要防的事故类型。

**R5｜单张不满意怎么重做**
单张提供两条路径，**不再追问弹窗**：
1. **原样重做**（同提示词，只换随机种子/重试一次）—— 用于模型偶发失败；
2. **改提示词后重做**（就地编辑该段提示词）—— 用于内容不对。
> 风险提示：`clips[i].prompt` 是**唯一提示词来源**，W2 分镜写的也是它，W5 视频也用这条。
> 就地改文案会**同时改变下游视频的运动描述**。这是预期行为（用户就是想改），但 UI 必须提示「这条提示词也会用于视频生成」。
> → 编号 Q11。

**R6｜驳回后回到哪一步（明确到步骤）**
按驳回**范围**分三档，不设第四档：

| 用户意图 | 回到哪 | 影响范围 | 后果 |
|---|---|---|---|
| 这张图不好，换个画法 | **W3**（仅该 index 重新出图） | 1 张 | 其它图、其它段的提示词全部不动 |
| 这几张的内容方向都不对 | **W2**（重新分镜，覆盖 `clips[*].prompt`） | 全部 | 会覆盖用户手改过的提示词，**必须二次确认** |
| 整体方向就错了，重来 | **W1**（改原始提示词重新建任务） | 新任务 | 旧任务保留在历史里，不删除 |

**禁止**「驳回 → 回到 W5」：W5 的输入就是图片，没有图就没有输入（除非走 R2 的跳过例外）。

**R7｜审核中的任务状态**
新增任务级状态 `awaiting_review`（命名与最终取值待研发确认，见 Q4/Q5）。
它必须表达：**流水线活着、但主动停在等人**，与 `failed`（进程中断/出错）、`paused`（旧的片段生成暂停）都不同。
> 映射：新状态；现有状态集合见 §2.2。

**R8｜绝不自动通过（本规格最强的一条）**
审核门**没有超时自动放行**。等 1 小时、1 天、1 周都停在原地。
理由：审核是**责任点**。自动通过等于「没人看过也算通过」，与 `AGENTS.md` §4.1（未执行 ≠ 通过）§4.8（不许谎报状态）同源。
> 代价：会长期存在「挂着没人管」的任务。缓解手段见 R9（不是放行，是**提示**）。

**R9｜长期未处理的处理方式 = 提示，不放行**
任务在 `awaiting_review` 停留超过 **24 小时**：
- 任务列表给出「待审 1 天」的角标（按停留时长排序）；
- 进入工作台时给一条一次性的顶部提示（可关闭）；
- **不改变任务状态，不发任何自动动作。**
> 判定：任何「超时后自动继续/自动失败」的实现都视为违反 R8。见 §9 Q10（关于保留多久、是否提醒）。

**R10｜部分通过的粒度**
允许「9 张通过 + 1 张驳回」共存为 `awaiting_review`（因为只要有一张没通过，整组就不能走）。
全组通过后状态才转为「审核通过」，解锁 W5。

**R11｜审核界面必须给判断依据，不能只给一张图**
每张图旁必须同时可见：① 该段提示词；② 序号与总张数；③ 画面尺寸/比例；
④ 「这张是合成图（Mock）」的标记（若命中 W3-d）；
⑤ 与前一张/后一张的**关系**（至少给序号导航，允许左右切换）。
> 理由：审核的本质是「这张图配不配这条文案」，缺了提示词就没法审。

**R12｜审核记录要能被追溯（但不做合规留痕）**
任务详情里保留：每张图的版本历史（第几次重做、第几版）、最终通过时间。
**不要求**记录「审核意见」「审核人签名」这类合规字段。
> 映射：可复用现有步骤记录结构（`task.steps[*].qcDetails` 风格，`taskManager.js:199-214`），或新增 `task.imageReview`。

## 5. 状态机（S1–S6）

现有状态集合见 §2.2。新增后的**任务级**状态必须满足：

**S1｜状态集合（建议，待 Q4 定稿）**
`pending` → `generating`(W1/W2) → `image_generating`(W3) → **`awaiting_review`(W4)** →
`generating`(W5) → `concatenating` → `looping` → `transcoding` → `mixing` → `final_qc` →
`completed` | `partial` | `failed`
外加已存在的 `paused`、`regenerating`、`processing`（本次不改语义）。

**S2｜互斥**
`awaiting_review` 与 `failed` 互斥；与 `paused` 互斥（两者都可能「停在原地」，但不能同时成立，
否则 `pause-state` 接口（`app/server.js:1553`）的语义会打架）。

**S3｜重启不得误杀**
`reconcileInterruptedTasks()` 的 `IN_PROGRESS`（`pipeline.js:988`）**必须显式排除**
`awaiting_review`、`image_generating`(若单独成态)、`paused`、`regenerating`、`processing`。
其中后三个是**既有缺口**，本次一并修（见 E3、Q5）。

**S4｜重启后的正向恢复**
审核中的任务重启后必须**回到 `awaiting_review` 并保留全部已生成图片的引用**，
而不是「因为进程不在了所以判失败」。判定：重启服务 → 打开任务 → 图还在、还能继续审、点继续能往下跑。

**S5｜旧数据兼容**
已存在的历史任务没有图片字段。读取时必须能正常显示（不报错、不留空白面板），
按「无审核记录（历史任务）」标注。见 E4。

**S6｜状态与步骤条的一致性**
任务级 `status` 与 `steps[].status` 不得互相矛盾（例：`status=awaiting_review` 时，
`steps.image_generation` 应为 `completed`，`steps.clip_generation` 应为 `pending` 而非 `in_progress`）。

| 档位 | 现有步骤（`pipelineStages.js:60/68-71/77/83`） | 新流程下的含义（产品建议） |
|---|---|---|
| `quick` | 核心链 + 拼接 | 核心链（含 W3 图片 + W4 审核）+ 拼接，**仍要审图**——因为不审就会生成付费视频 |
| `daily` | 核心链 + 拼接 + 循环 + 转码 + 配乐 | 同左，W3/W4 在核心链内 |
| `final` | 全部 8 步 | 全部 + W3/W4 |
| `clips_only` | 仅核心链（`fragmentOnly`） | 核心链到 W5 出片段为止，**仍要审图** |

## 7. 异常路径 E1–E10

每一条都要求：**用户看到什么 / 系统实际做什么 / 绝不能做什么**。

### E1｜图片生成单张失败
- **用户看到**：该位置一张明确的失败卡（原因 + 「重做这张」按钮），其余张正常显示。
- **系统**：其它张继续；整组进入 `awaiting_review` 但**不可整组通过**（R4）。
- **绝不能**：静默跳过该段、或把失败位显示成空白图。
- **映射**：现有片段级失败语义 `partial`（`pipeline.js:1226-1229`）；单点重做接口先例 `POST /clips/:index/regenerate`（`app/server.js:1566`）。

### E2｜图片生成整组失败（配置/Key/额度）
- **用户看到**：W3 步骤红叉 + 一句话原因 + 明确的下一步（去设置填 Key / 换模型 / 显式改走纯文生视频）。
- **系统**：任务停在 W3，**不自动改档位、不自动降级到文生视频**。
- **绝不能**：用 Mock 图冒充成功继续跑（`AGENTS.md` §4.8）。现状 `imageGen.generateImage()` 已经是「抛明确错误而不是返回假图」（`imageGen.js:104-117`），**这个行为要保持**。

### E3｜服务重启（本规格最危险的一条）
- **事实**：`reconcileInterruptedTasks()`（`pipeline.js:987`）会把 `IN_PROGRESS`（`:988`）里的任务一律标 `failed`。
- **用户看到**：审核中的任务重启后**仍在待审列表，图还在，可以继续审**。
- **系统必须做**：
  1. `awaiting_review` **不在** `IN_PROGRESS` 列表里（S3）；
  2. 重启后该任务的 `steps.image_generation` 仍是 `completed`，图片引用仍有效；
  3. **顺带修既有缺口**：`paused` / `regenerating` / `processing` 目前不在 `IN_PROGRESS`、也不会被恢复，
     重启后**永久卡死**（§2.3）。这三个要么进回收名单，要么进恢复流程，不能维持现状。
- **绝不能**：把「等一下人」当成「进程中断」。
- **⚠️ 验收脚本牵连**：`AGENTS.md` §2.2 记录了 `scripts/verify-pipeline-fixes.js`（28 项）在测这条回收逻辑；
  改 `IN_PROGRESS` 必须同步该脚本，不能删断言（`AGENTS.md` §2.2 对前端脚本有同样要求）。

### E4｜旧任务补跑时没有图
- **场景**：改造前已存在的任务（有片段视频、无图片）。
- **事实**：补跑 `continueTask` 会按档位算 `pending`（`pipelineStages.resolveResume:226`），
  且会复用「已成功且文件仍在」的片段（`AGENTS.md` §6「补跑」节，实测文件 mtime 未变）。
- **产品决策**：旧任务**不允许被审核门拦住**。判定依据是「该任务没有图片产物」，
  标记为 `image_review: 'legacy_no_image'`，**显式跳过**审核门并在任务详情里显示
  「历史任务：未经过图片审核（改造前创建）」。跳过必须带 `legitimateSkip` 语义与理由
  （`AGENTS.md` §4.1：只有业务上本就不适用才允许合法跳过）。
- **绝不能**：① 让旧任务因为「没有图」而永远无法补跑；② 反过来「没有图 = 自动通过」却不留痕。
- **卡点**：判定「一个任务是否经历过图片门」的依据是什么（有 `imagePath`？有阶段记录？版本号？）→ **Q12**。

### E5｜没有可用的图生视频模型
- **事实**：`IMAGE_INPUT_CAPABILITY`（`imageGen.js:80-87`）与 `/api/models.supportsImageInput` 目前除 `mock` 外**全为 `null`（未核实）**。
- **用户看到**：进入 W5 前就明确提示「当前模型未核实支持图生视频」，并给出可选项：
  换模型 / 去设置 / 显式选择「纯文生视频（放弃图片审核）」。
- **绝不能**：`null` 被当成 `true` 直接调用，或 `null` 被当成「不支持」直接失败而不给解释。
  `null` 的语义在代码注释里已写明（`imageGen.js:74-79`、`generators/index.js` 工作区改动）——**UI 必须原样表达三态**。

### E6｜Mock 降级与审核门冲突
- **场景**：`IMAGE_GEN_*` 没配 Key，但用户已经点了生成。
- **产品决策**：若图片走 Mock，审核页必须把每张图标成「合成图」，并且**整组通过按钮的文案改为
  「这些是合成图，确认继续（将消耗真实视频生成费用）」**。
- **理由**：现状已能识别 Mock 降级（`task.mockFallback`，`pipeline.js:1195`；`AGENTS.md` §6 有完整背景），
  审核门不能变成「对着测试图案点通过」。

### E7｜重复生成产生费用与文件覆盖
- **产品决策**：图片重做**不覆盖**旧版（W3-c），视频重做沿用现有 `_vK` 语义。
- **映射**：`AGENTS.md` §6「重新生成/重试不再覆盖已有片段文件」的既定原则与事故记录；实现参考 `pipeline._nextClipPath()`。
- **待确认**：图片版本保留多久、磁盘怎么清（→ Q10）。

### E8｜审核时任务被删除
- **用户看到**：提示「任务已被删除」，自动退出审核界面。
- **系统**：删除走后端已有逻辑 `DELETE /api/tasks/:id`（`app/server.js:1656`）+ 回收站
  `POST /api/trash/:id/restore`（`:1662`）、`GET /api/trash`（`:1674`）。
- **绝不能**：前端继续对着已删任务发审核请求并静默失败。

### E9｜同一任务两个标签页同时操作
- **事实**：现有接口无版本校验（未核实是否有，需研发确认）。
- **用户看到**：后提交的一方收到「该任务状态已变化，请刷新」，而不是覆盖对方的判定。
- **绝不能**：两边的审核结果互相覆盖而用户不知道。
- **卡点** → **Q9**。

### E10｜审核门后视频生成中断（含 E3 的兄弟场景）
- **场景**：W5 跑到一半进程挂了。
- **系统**：现状会被 `reconcileInterruptedTasks` 判 `failed` 并提示「可补跑」（这是**正确**行为，不要改），
  但补跑必须能**从已成功的片段继续**，且**不需要重新审图**（图已通过）。
- **映射**：补跑 `continueTask`（`app/server.js:1590`）+ `resolveResume`（`pipelineStages.js:226`）。

## 8. 本期不做（N1–N10）

> 写清楚「不做」比写清楚「做」更重要——它防止范围在实施中被悄悄扩大。

| 编号 | 不做的事 | 理由 |
|---|---|---|
| **N1** | 多用户 / 角色权限 / 审批流 / 会签 / 抄送 | 用户明确：单人操作，无审批流无角色。做了是纯浪费，还会把界面变复杂。 |
| **N2** | 审核超时自动放行 / 自动失败 | 违反 R8。审核是责任点，自动通过等于「没人看也算通过」。 |
| **N3** | 用模型自动判定图片质量并代替人工通过 | 可以把模型评分当**参考信息**展示，但**不得**据此自动通过。依据 `AGENTS.md` §4.1/§4.2。 |
| **N4** | 视频片段的逐段人工审核 | 本期的门只在**图片**。视频段靠质检 + 补跑兜。原因：视频观看成本远高于图片，逐段看视频会让流程卡死。 |
| **N5** | 跨任务的批量审核队列 | 本期只做「任务内的整组/逐张审核」+「待审任务列表」。批量工具留到有真实积压再说。 |
| **N6** | 图片的多版本并排对比 / diff 视图 | 支持版本历史与回看，但不做「两版并排打分」这种专业工具功能。 |
| **N7** | 移动端 / TV 端适配 | 屏保播放是**输出物**，不是操作端。操作端按桌面软件做。 |
| **N8** | 国际化 | 单语言（中文）。 |
| **N9** | 把 ffmpeg 换成云端渲染 / 多机并发 | 与本次前端重做无关，改了会引入部署复杂度。 |
| **N10** | 图片生成接入多家并做自动选优 | 本期最少接**一家**跑通链路；多家比价/择优是下一期。 |

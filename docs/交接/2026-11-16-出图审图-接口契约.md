## 1. 触发与字段（task 级）

开启条件（全部满足才走新链路）：

1. `task.runtimeConfig.imagePerClip === true`；
2. 任务不在 `source==='library'` / `source==='regenerate'`（那两条链路片段已存在，不出图）；
3. 该次运行确实还有「没有可用首帧图」的片段。

**`task.runtimeConfig` 新增字段**（全部字符串，除最后一个）：

| 键 | 含义 | 对应 ImageGenerator 覆盖键 |
|---|---|---|
| `imageApiKey` | 出图 Key（只在内存；落盘由 `redact` 清空） | `IMAGE_GEN_API_KEY` |
| `imageBaseUrl` | 出图 Base URL | `IMAGE_GEN_BASE_URL` |
| `imageProvider` | 出图厂商标识（如 `dashscope`） | `IMAGE_GEN_PROVIDER` |
| `imageModel` | 出图模型（如 `wan2.7-image`） | `IMAGE_GEN_MODEL` |
| `imageSize` | 出图尺寸（如 `1696*960`） | `IMAGE_GEN_SIZE` |
| `imagePerClip` | boolean，是否逐段出图 | —— |

未传的键 = 回落到 `.env` 的 `IMAGE_GEN_*`（与 `/api/images/*` 现有口径一致）。

**`task.imageReview`（持久化，供 UI 与补跑判断）**

```js
task.imageReview = {
  required: true,
  total: <段数>,
  generated: <本次真正出图张数>,
  reused: <复用已有图的张数>,
  failed: <出图失败张数>,
  failedIndices: [<0-based 片段下标>],
  photoIds: ['<taskId>_img_<index>', ...],
  generatedAt: ISO,
  reviewedAt: ISO | null,      // 用户点「继续/补跑」后写
  autoApproved: <继续时把 pending 视为通过的张数>,
  rejectedClips: [<0-based 下标>],
  settledBy: 'unpause' | 'continue' | null
}
```

**`task.awaitingImageReview`**：boolean，只有「正在暂停等审图」期间为 true；结算后清掉（`false` 或删除）。

**`task.clips[i]` 新增/使用字段**：
- `clip.photoId` —— 首帧图 id（图生视频既有字段，`_i2vPayload` 只用它）；
- `clip.imageStatus` —— `'generated' | 'failed'`（仅出图链路写，便于 UI/排障）；
- `clip.imageError` —— 出图失败原因（字符串，最长 500 字）。

## 2. 后端行为（`src/pipeline.js`）

### 2.1 前置步骤位置

在 `_runPipeline` 的**片段生成步骤开始之前**（即 `taskManager.recordStepStart(taskId, 'clip_generation')` 之前）执行：

```
if (条件满足) {
  const r = await this._generateClipImages(taskId, task);   // 逐段出图（幂等）
  if (r.generated > 0 && 需要审图) {
      → 进入审图暂停（见 2.3）
  }
  await this._settleImageReview(taskId, 'unpause'|'continue')   // 幂等（正常路径由 unpause 触发）
}
```

- **不新增 pipelineStages 的步骤键**（`pipelineStages.ALL_STAGES` 不动，避免 `verify-stages` 语义变化）；
  事件记录到任务字段 `imageReview` + `console.log`，**不要**写进 `task.steps`。
- 出图本身**不写阶段状态**，所以 `_stageEnabled('clip_generation')===false`（补跑从拼接开始）时也要
  走幂等判断：所有片段都已有可用 `photoId` → `generated=0` → 立刻返回。

### 2.2 逐段出图（`_generateClipImages`）

> **实现补充（2026-11-16 16:00 落地、已验收，行为以代码为准）**：
> a. **用户明确打回的图本次不自动重出**（`_isUserRejectedClip`，pipeline.js `imageStatus==='failed'` +
>    `imageError` 以「图片被打回」开头）：直接交 §2.5 守卫判该片段失败。否则自动重出图 + 继续时
>    「pending 视为通过」会把新图自动 approve，等于绕过审图门，并产生一次未获用户同意的图片计费。
> b. **不替「视频已成功」的片段出图**：`clip.status==='success'` 且视频文件仍在 → 跳过（从拼接起
>    补跑时不该再花图片钱）。
> c. **重出图换 id**：若 `<taskId>_img_<index>` 已有记录（被打回后重出），用 `_vN` 后缀新建条目
>    （`_nextImageId`），否则 `photoLibrary.ingest` 的幂等规则会保留旧文件/旧审核状态，新图等于白出；
>    `_vN` 会被 `inferGroupId` 归到同一版本组。

1. 解析覆盖键（见 §1 表）→ `getImageGenStatus(overrides)`；`usable !== true` →
   **抛错并让任务失败**，文案包含 `出图未就绪`、缺失项/未注册厂商、指向「设置 → 图片生成」。
   **绝不降级成文生视频**、绝不返回占位图。
2. 需要出图的片段：`clips.filter(c => !(c.photoId && photo 存在 && 文件存在 && status !== 'rejected'))`。
   已有可用图的片段计入 `reused`，不重复计费。
3. 预算闸门：`budget.estimateImage(需要张数)` 与 `budget.canAfford` 不通过 →
   任务失败，错误含 `余额不足` 与需张数/剩余额度（与 `/api/images/generate-batch` 同口径）。
4. 并发出图（默认 3，`IMAGE_GEN_CONCURRENCY` 可覆盖，上限 6）：
   - prompt = `clip.imagePrompt || clip.prompt`（场景卡任务由 `promptComposer.composeImagePrompt` 产出）；
   - `generator.generateImage(prompt, {taskId, index, size, negativePrompt: clip.negativePrompt, outDir: config.STORAGE.clipsDir})`；
   - 成功 → `photoLibrary.ingest({id: photoLibrary.makeId(taskId, index), taskId, index, filePath,
     url:'/clips/'+basename, prompt, negativePrompt, provider, model, size, width, height,
     status:'pending', source:'generation'})`（**待审**，不是 approved）→
     `taskManager.updateClip(taskId, index, {photoId, imageStatus:'generated'})` →
     `budget.reserve({usd: budget.estimateImage(1), kind:'image', taskId, meta:{source:'pipeline-image-first', index}})`；
   - 失败 → `taskManager.updateClip(taskId, index, {imageStatus:'failed', imageError: msg})`，**不自动重试**
     （重试 = 额外真实计费，只能用户点「补跑」触发）。
5. 写 `task.imageReview`（§1 结构，`reviewedAt:null`），`generatedAt=now`。

### 2.3 审图暂停（一次性）

- 条件：本次 `generated > 0` **且** (`!task.imageReview` 或 `task.imageReview.reviewedAt == null`)。
- 动作：
  ```js
  this.pausedTasks.add(taskId);
  taskManager.updateTaskStatus(taskId, 'paused', {
    currentStep: `等待审图：已出 ${n} 张（待审 ${p} / 失败 ${f}）`,
    awaitingImageReview: true
  });
  const ok = await this._waitIfPaused(taskId, this._imageReviewMaxWaitMs());
  if (!ok) return { success:false, aborted:true, failureCode:'image_review_timeout' };
  ```
- 超时上限：`process.env.IMAGE_REVIEW_MAX_WAIT_MS`，默认 **24 小时**（`24*3600*1000`）。
  超时后 `_waitIfPaused` 既有逻辑会把任务标 `failed`；本步骤额外写
  `failureCode='image_review_timeout'`、`recoverable=true`、文案指向「补跑」。
- 暂停期间**不**启动片段生成、**不**花视频的钱。

### 2.4 审图结算（`_settleImageReview(taskId, settledBy)`，幂等）

在下列三处调用（幂等，`reviewedAt` 已存在则直接返回）：

1. `resumeTask(taskId)`（`POST /api/tasks/:id/unpause`，用户点「继续」）；
2. `continueTask(taskId)`（`POST /api/tasks/:id/continue`，重启/失败后「补跑」）；
3. `_runPipeline` 里审图等待返回 `true` 之后（兜底）。

动作：

- 该任务所有 `photoId` 对应的照片：
  - `status === 'pending'` → `photoLibrary.markReviewed(id, 'approved', '审图暂停后继续，未单独审核视为通过')`，
    计入 `autoApproved`；
  - `status === 'rejected'` → 对应片段 `taskManager.updateClip(taskId, i, {status:'failed',
    error:'图片被打回（第 N 段），不会用这张图生成视频；请重出图或改选图后再补跑'})`，记入 `rejectedClips`；
  - `status === 'approved'` → 不动。
- 写 `imageReview.reviewedAt=now`、`autoApproved`、`rejectedClips`、`settledBy`；
  `awaitingImageReview=false`；`currentStep='视频片段生成'`。
- **不做**任何真实计费调用。

### 2.5 缺图禁止降级（`_batchGenerate` 内新增守卫）

`imagePerClip === true` 的任务，进入单片段生成前必须校验：`clip.photoId` 存在、照片存在、
文件存在、`status === 'approved'`。任一不满足 → 该片段直接 `failed`，错误含
`缺少首帧图，拒绝降级为文生视频`（出图失败/图片被打回都走这里），**不发视频请求**。

### 2.6 补跑闸门修正（`continueTask`）

现有硬闸门 `needsConcat && !completed.includes('concatenation')` 会让「片还没生成」的任务永远
无法补跑（错误：`补跑需要拼接产物…`）。

**修正（2026-11-16 14:20 收窄版，已批准）**：放行条件是**两个都满足**：

1. `resume.pending.includes('clip_generation')`（本次会把片段生成出来，拼接输入自然会产出）；
2. **任务确实已经开始过**（`startedAlready`）：`completed.length > 0`
   **或** `task.imageReview` 存在 **或** `Object.values(task.steps||{}).some(v => v && ['completed','reused','failed','partial'].includes(v.status))`
   **或** 任一片段 `attempts > 0`。

其余情形（尤其是**从未启动过的 pristine 任务**，steps 全 pending、completed 为空）保持原报错
`补跑需要拼接产物，但拼接尚未完成；请先跑完到拼接步骤` —— 这正是
`scripts/verify-continue.js` [4] 的断言场景，不得放行。

### 2.7 监督器（`src/assistant/supervisor.js`）

- `taskView(task)` 增加：`awaitingImageReview: !!task.awaitingImageReview`、
  `imageReview: task.imageReview ? { total, generated, failed, reviewedAt,
  pendingPhotos, approvedPhotos, rejectedPhotos } : null`
  （三个计数按 `photoLibrary.get(photoId).status` 现算；取不到的算 pending）。
- `tick()` 在 `task.status === 'paused' && task.awaitingImageReview` 时，**每计划只追加一次**
  会话消息（用 `memory.appendMessage`，`kind:'state'`）：
  「图出好了（N 张）。到「库 · 图片」抽看/通过/打回，然后点「继续生成」我再开始生成视频。」
- 不要改状态机状态集合（paused 已在 `ACTIVE_STATUS`）。

### 3.5 图片手动调色（新增）

`POST /api/photos/:id/adjust`

```jsonc
// 请求（二选一）
{ "brightness": 0, "contrast": 0, "saturation": 0, "temperature": 0 }   // 各 -100..100，整数
{ "reset": true }                                                      // 回退到原图
```

- 语义：参数是**绝对值**（不是增量），每次都从**原图**重新渲染，避免反复叠加掉画质。
- 响应 200：`{ ok:true, adjusted:boolean, reverted:boolean, filter:'…'|null, url, photo }`
  （`photo` 为更新后的图片条目，含 `adjust` 结构）。
- 错误：400（参数非法/全 0 且非 reset）、404（图片不存在）、409（原图文件不存在）、502（ffmpeg 失败）。
- 调色**不计费**（本地派生），photo 条目的 `cost` 不改写；`source` 保持原值。
- 不允许把调色派生图当成「新生成图」入库；版本链保留在同一 photo 条目里：

```js
photo.adjust = {
  params: { brightness, contrast, saturation, temperature } | null,
  appliedAt: ISO,
  originalPath, originalUrl, originalWidth, originalHeight, originalSizeBytes,
  current: { filePath, url, width, height, sizeBytes, version },
  versions: [ { version, params, filePath, url, appliedAt } ]   // 每次应用追加，最多保留 20 条
}
```

- 实现落在 `src/processors/photoAdjust.js`（新模块，`be-photo` 拥有），路由只做校验 + 调用 + 写库。

## 4. 图片调色渲染契约（`src/processors/photoAdjust.js`）

```js
PARAM_RANGES = { brightness:[-100,100], contrast:[-100,100], saturation:[-100,100], temperature:[-100,100] }
normalizeParams(raw)  // → {brightness,contrast,saturation,temperature}，非数字/越界 → throw（E_BAD_PARAM）
buildFilter(params)   // → 'eq=brightness=…:contrast=…:saturation=…[,colorbalance=rs=…:bs=…]'
applyToPhoto({ photo, params, outDir, ffmpegPath, originalPath })  // → { ok, filePath, width, height, sizeBytes, filter, version }
revertToOriginal({ photo, originalPath })  // → { ok, filePath, width, height }
```

- 输出：`<outDir>/<photoId>_adjust_v<N>.png`，**不覆盖**任何已有文件（`N` 递增）。
- 一律 `execFileSync(ffmpegPath, args)` 传数组参数（AGENTS §14：禁止字符串拼接命令）。
- ffmpeg 失败 → 抛错（带 stderr 末尾 400 字），绝不返回成功。
- 先写临时文件再 `rename`（原子），失败清理临时文件。

## 6. 验收要求（零计费）

- 所有验收脚本必须**零真实计费**：出图用本地 stub 适配器（`registerImageProvider`），视频用 Mock 模型。
- 每个新脚本自报 `N 通过 / M 失败`，失败 `process.exit(1)`；重复跑要能自清理（临时目录 + 删任务）。
- 后端脚本用临时 `CLIPS_DIR` / `PHOTOS_DIR` / `DATA_DIR` 等环境变量，**不污染真实库**。
- 负向证据必须有：出图未配置 → 失败且不降级；图片被打回 → 对应片段失败；参数越界 → 400；
  ffmpeg 失败 → 502/抛错；跳过（skip）不得当通过。
- 结论分「通过 / 不通过 / 未验证」；3001 未重启前，后端新代码一律标「未验证（运行中仍是旧进程）」。

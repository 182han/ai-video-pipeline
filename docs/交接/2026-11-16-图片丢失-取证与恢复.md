`app/scripts/purge-artifacts.js`：

- `collectRefs()`（48–71 行）只读 `data/tasks/*.json` 与 `data/library/*.json`，**没有 `data/photos`**。
- `listTargets()`（90–98 行）把 `clips/` 中所有**未被 refs 命中**的文件归为「clips-孤儿文件」，不区分扩展名。
- 这 17 张照片的引用关系：14 张 `v31test_*` 的 `taskId` 为 `null`；`real_test_*`、`ui_img_*` 的 task JSON 已不存在 → 在 tasks/library 里都查不到 → 全部落进「孤儿文件」。
- 讽刺的是脚本注释第 13 行写着「绝不碰 data/photos」——它确实没进 `data/photos` 目录，但删掉了 `data/photos` 记录所指向的 `clips/*.jpg|png` 文件。
- `DIR_PATTERNS`（35–38 行）含 `/^v31-/i`、`/^final-image-set-review$/i`，两个 output 目录正是被这条规则命中。

## 5. 根因与防再发

### 5.1 根因链

1. `purge-artifacts.js` 的引用收集**漏了 `data/photos`**（也漏了 `data/projects`、`data/assistant` 等可能的引用源）→ 图片库独占引用的文件被误判为孤儿。
2. 脚本按「clips 里所有未被 tasks/library 引用的文件」清理，**不按扩展名/库归属做保护**；17 张图片混进 462 个孤儿文件中，仅以「19.7 MB」汇总出现。
3. 清理执行者只看了聚合摘要（「孤儿片段 19.7 MB」），**没有展开 17 个图片文件名**，也没有在硬删前核对 `data/photos` 的 17 条记录。
4. 软移入与硬删除之间只隔 **约 1 分钟**，没有保留期/二次确认，导致「可人工找回」的 `--apply` 设计被立即抵消。
5. 文档记录出现「移出并彻底删除」与「6 张缺失」两种口径，直到 P3 才纠正为 17/17，延误了最佳恢复窗口（但本次仍靠 Chrome 缓存救回）。

### 5.2 建议（代码与流程）

**代码层（研发）**

1. `collectRefs()` 增加 `data/photos/*.json`（读 `filePath`/`fileName`），并建议扫描所有 `data/*Library*` 目录。
2. 增加保护规则：`clips/` 下的 `.jpg/.jpeg/.png/.webp` 默认不参与「孤儿清理」，除非 `--include-images` 显式开启。
3. `--hard` 不应与 `--apply` 在同一流程里使用；新增独立的 `--purge-trash`，要求：
   - 先打印按扩展名/类别统计（图片数、视频数、JSON 数）；
   - 图片数 > 0 时必须 `--confirm-images` 二次确认；
   - 建议保留期（如 7 天）或至少要求跨会话/跨时间执行。
4. manifest 增加 `sha256` 与 `mtime`，并在服务日志中输出**文件级清单**（不只聚合）。
5. 新增验收脚本 `verify-purge-refs.js`：构造「只在 data/photos 被引用」的图片，断言 dry-run 不把它列为目标（负向用例）。

**流程层（所有窗口）**

6. 清理前后跑一次「引用完整性检查」：`data/photos`、`data/library`、`data/tasks` 中引用的文件若出现在 `data/trash`，立即中止硬删。
7. 「用户批准清理」不等于「批准删除图片库/成片」；硬删前必须把**非测试类别**单独列给用户确认。
8. 交接文档不要只写聚合体积；至少列出被删目录名与文件类型统计。

### 5.3 责任归属（事实层面）

- **直接执行者**：Phase 0/P1 窗口（会话 `5a4e171d-7c10-4143-8dc8-c4c5816392cc`），2026-11-15 17:49:06–09 的 PowerShell `Remove-Item`。
- **授权背景**：用户 2026-11-14 22:45 批准「档 A 全删」（测试残留），2026-11-15 17:37/17:40 批准 Phase 1 开工；**没有**单独批准删除图片库文件。执行者把「清空 trash」视为该授权的延伸。
- **工具缺陷**：`purge-artifacts.js` 的引用范围漏 `data/photos`，是本次误删的**必要条件**；即使人工逐项看，17 个图片也藏在 462 个孤儿文件里，没有按类型提示。
- **文档责任**：handoff/changelog 如实记录了「彻底删除 1307.7 MB」，但没有列出 17 张图片；同一文档「6 张缺失」的口径错误进一步延误定位。
- **结论**：属于**清理脚本引用范围缺陷 + 执行时未逐项复核 + 软删除后立即硬删**的复合流程事故；不是恶意删除，也没有证据表明有人隐瞒。用户批准的是「清理测试残留」，图片文件是被脚本误分类后一并清除的。

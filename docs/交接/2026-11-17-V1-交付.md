## 5. 行为变更（比设计文字多出来的，必须让下一个窗口知道）

1. **顺序取卡 → 随机抽卡 + 跨计划冷却**（§9.1-4 的产品决定 Q24=B/Q25=A/Q30=C）。
   - 影响：`sceneCards.allocate()` 不再返回「卡库前 N 张」；`nextSwapCandidate()` 不再返回「文件顺序的下一张」。
   - 不变：不放回、不用 buffer、耗尽的报错语义、`planFromIds()`（显式 ids 路径完全不变）、取满 180 张时结果与旧行为一致。
   - 计划内稳定：`plan.buildPlan` 阶段就把卡固定进 `sceneCardIds`；旧计划（无 ids）的只读预览用 `seed=planId` 稳定。
2. **buffer 选择改为「优先不撞 scene_key」**（随机抽卡的连带修复）。
   实测 20 张 buffer 的 `scene_key` 全部与它 `variant_of` 的原卡**相同**；顺序取卡时几乎撞不上，
   随机抽卡后可能撞上，导致同一任务里出现两个相同 `scene_key`（审计键重复）。
   现在 `replaceWithBuffer()` 优先挑不撞的；没有不撞的才回退第一张未用 buffer（耗尽语义不变）。
3. **新增两个意图**：`confirm`（§9.1-6）与 `context`（§9.1-7）。`classify()` 的既有分类全部回归验证（含 164 条基线里的旧断言）。
4. **「用这个：…」/「把 X 改成 Y」不提升成 memory 的全局意图**，而是 supervisor 会话层兜底
   （`isPlanPromptEditForm` + 只对 `unknown/create` 改判），避免抢「把默认通道改成百炼」这类 V2 设置句；
   同时挡住「不要配乐 / 不要场景卡 / 取消出图」这类关开关句（否则会被 diff 正则当成"删除"）。
5. **卡片可见性**：除两个时点外，收到其它回复时会把卡片收起（不是"保持可见"）；点确认成功后再收起（防重复建任务）。

## 6. 未验证项 / 既存失败（明确不计入通过）

### 6.1 浏览器真实交互 —— **未验证**
本轮不重启 3001（用户持有该进程），而 `web/**` 是静态文件、`src/**` 是启动时加载：
- 前端改动（`assistant.js`）**刷新页面后对新代码生效**，但后端 `/api/assistant/message` 仍是旧代码，
  不会返回新的 `intent=confirm/context`，所以「卡片两时点 + 确认门」的**真实点击手感不可能在本轮验证**。
- 因此 UI 部分只做**静态断言**（3 条：`planCardVisible` 两处渲染点、两时点置真条件、execute 只由 onConfirm 触发）。
- 自测方法（下一个窗口/重启后）：`node server.js` 重启 3001 → 打开 `/app` → 说「10 分钟」看卡片是否只弹一次 →
  说「把第 2 段的提示词给我看一下」（不应弹卡）→ 说「确认生成吗」（应弹卡）→ 点「确认执行」（只建 1 条任务）。

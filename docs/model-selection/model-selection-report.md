# 视频生成模型选型报告：为什么选择万相 3.0

> 面向对象：项目负责人 / 汇报评审
> 结论口径：**同题、同分辨率下的可用性对比**（不是全网画质评测）
> 证据来源：项目内 `app/data/tasks/*.json` 真实任务记录、`app/clips/` 实测媒体属性、各家官方文档与价目表（2026-10 口径）
> 撰写：2026-10-25

---

## 一、一句话结论

**万相 3.0 是本项目当前唯一被真实跑通、且能稳定输出 720P 的自然风光视频生成模型；选择它的核心理由不是“画质最强”，而是“在 720P 这个我们真正需要交付的分辨率上，它是唯一有实测数据的生产级选项”。**

这份报告同时说明：**这个结论有明确边界**。可灵 3.0 是唯一能进同一张考卷、且目前尚未测试的对手；报告最后给出了把它测出来的具体方法。

---

## 二、项目约束（决定了什么模型才合格）

| 约束 | 事实 | 对选型的影响 |
|---|---|---|
| 交付形态 | Android TV 屏保循环长片，30 分钟以上 | 需要大量片段，单段成本和失败率是核心 |
| 交付分辨率 | 720P 足够，1080P 加分 | 模型必须**原生支持 720P**，而不是先出 480P 再放大 |
| 素材主题 | 自然风景、户外、宇宙、极光 | 需要模型对“地貌质感、光的方向、慢运动”稳定 |
| 流水线 | 分镜 → 批量生成 → 质检 → 拼接 → 循环 → 配乐 → 转码 | 模型必须能融进异步任务 + 重试 + 质检 |
| 并发与重试 | 并发 3、重试 1 次 | 失败计费会单向放大成本 |
| 提示词 | 项目自带模板优化器，会自动追加运镜/光影/质感 | 模型的 prompt 智能改写必须可关 |
| 音频 | 项目自带配乐 | 模型自带音轨必须可关 |

## 三、项目里实际接入的模型与真实进度

代码层面 `app/src/generators/` 已接入 6 个生成器。真实调用情况如下（来自 `app/data/tasks/`）：

| 模型 | 真实调用记录 | 结果 |
|---|---|---|
| **万相 3.0**（`dashscope`） | 4 条任务 | 3 条成功（10 段付费片段），1 条因 NSFW 质检未执行失败 |
| 硅基流动 Wan 2.2（`siliconflow`） | 2 条任务 | 1 条成功（2 段 1280×720），1 条余额不足 |
| 可灵 3.0（`kling`） | 0 | 仅代码接入 |
| Seedance 2.5（`seedance`） | 0 | 仅代码接入 |
| Agnes 2.5（`agnes`） | 0 | 仅代码接入 |
| Mock | 若干 | 测试图案，非真实内容 |

**这条表是整份报告最重要的一行结论**：在“同题同分辨率”的语境下，只有万相 3.0 和硅基流动做过真实的 720P 生成，后者此后因余额问题中断。

## 四、能力参数对比（官方口径，2026-10）

| 项 | 万相 3.0 | 硅基流动 Wan 2.2 | 可灵 3.0 | Seedance 2.5 |
|---|---|---|---|---|
| 分辨率档位 | 480P / 720P / 1080P | 固定 1280×720 | 720P / 1080P / 4K | 480P / 720P / 1080P（项目适配层仅暴露前两档） |
| 单段时长 | 2–30 秒（可传 -1 智能时长） | 5 秒 | 3–15 秒 | 4–30 秒 |
| 出声开关 | 有，`audio` 可关 | 无该参数 | 按是否有声分档计费 | 无该参数 |
| 提示词智能改写 | 有，`prompt_extend` 可关 | 无 | 无 | 无 |
| 负面提示词 | 未作为独立字段暴露 | 支持 | 支持（≤2500 字） | 未暴露 |
| 首帧/首尾帧输入 | 支持（first_frame / last_frame） | 不支持 | 支持 | 支持 |
| 输出帧率 | 30 fps | 实测 16 fps | — | — |
| 计费 | 按秒，失败不计费 | 按平台套餐 | 按积分/秒 | 按套餐/秒 |
| 项目里的实测片段数 | 10 | 2 | 0 | 0 |

**关键差异解读：**

1. **分辨率**：只有万相与可灵同时提供 720P 与 1080P。“同题同分辨率对比”真正的候选池只有这两个。
2. **时长**：万相 30 秒，意味着同样一条 30 分钟成片需要的片段数约为可灵方案的一半，出错概率与质检开销同步下降。
3. **可关项**：`audio` 与 `prompt_extend` 都能关，这对“项目自己有配乐、自己有提示词优化器”的我们是决定性优势——否则会和自己的流程打架。
4. **帧率**：万相实测 30fps，硅基流动 Wan 2.2 实测 16fps。屏保长片在 16fps 下运动感会明显不足。

## 六、成本视角

按项目默认口径（每段 6–7 秒、720P）：

- 30 分钟成片约需 **300 段**，合计约 **1,800–2,100 秒**生成时长。
- 万相 3.0 标准版 720P 官方 **0.6 元/秒** → 约 **1,100–1,300 元**理论成本（失败不计费）。
- 若改 1080P（1.2 元/秒），成本翻倍。
- 可灵与硅基流动按各自积分/套餐计价，需用当期单价换算后比较；本报告不擅自折算。

**真正的成本变量不是单价，而是质检失败率**：10-19 那次 10 段全部因 NSFW 质检未执行被判失败，相当于一批片段白花钱却进不了成片。

---

## 七、为什么选择万相 3.0（写进报告的正式理由）

1. **唯一在原生的 720P 档位上跑通整条流水线**：出片段、进质检、拼成片、做循环，全流程有真实记录。
2. **时长与分辨率两条硬指标都覆盖**：2–30 秒、480P–1080P，一次配置就能支撑“日常 720P + 关键镜头 1080P”的双轨策略。
3. **可关的 audio 与 prompt_extend**：不干扰项目已有的配乐与提示词优化。
4. **失败不计费**：与项目“并发 3 + 重试 1”的机制兼容，重试不会放大成本。
5. **适配层经过实战验证**：状态映射、下载、降档逻辑都已在真实任务中跑过。

---

## 八、已知局限（必须在报告里如实写）

1. **没有与可灵/Seedance 的同题样本**，因此“画质最好”不成立，只能说“当前唯一跑通”。
2. **天空与水面在过度压缩或大幅放大时会失去细节**（7.2 Mbps @720P 的输出拉到 4K 会涂抹）。
3. **模型成功率 ≠ 流水线成功率**：NSFW 质检配置不当会让成功生成的片段全部作废。
4. **历史里存在 480P 失败与 720P 暂停**，单次成功不构成稳定结论，至少需要 3 次重复的有效样本。

## 九、下一步：把报告从“选择说明”升级为“选型结论”

建议做一次受控实验：

- **变量固定**：同一批 3 条提示词、同一分辨率（720P）、同一时长（6 秒）、同一批质检配置。
- **被测对象**：万相 3.0、可灵 3.0、硅基流动 Wan 2.2。
- **重复次数**：每组合 3 段。
- **样本量**：3 × 3 × 3 = 27 段。
- **评判指标**：blurdetect 均值（清晰度）、YAVG 与过曝帧（曝光）、主观单帧（构图与主体是否清晰）。

评估用的 PowerShell 命令见配套 HTML 报告的“自己做一次同题对比”一节。

## 十、附：关于“你能不能现在生成视频”

**不能。** 当前项目中所有视频生成 Key（万相、可灵、Seedance、硅基流动、Agnes）均为空，配置里没有可用的 API 凭据，因此无法调用任何一家模型去生成新片段。本报告所有结论均基于历史记录与公开资料，未执行新的付费生成。

如需看到新画面，需在项目设置中填入真实 Key，然后在页面里跑一次任务。

## 2. 风险清单：六条我不能全面肯定的判断

> 这一节是本方案的核心。用户明确要求"不能全面肯定"，以下每条都指向一个必须先决策、否则必然返工的问题。

### R1. 你给的 5 个参考站，全部是"组件 / 动效库"，不是"工具型产品"参考

| 站点 | 性质实测判断 | 对"工具"的帮助 |
|---|---|---|
| reactbits.dev | React 动效组件库 | 仅视觉语汇；**强绑 React** |
| ui.aceternity.com | React + Tailwind 组件库（Aceternity UI） | 仅视觉语汇；**强绑 React + Tailwind** |
| uiverse.io | 纯 CSS/HTML 组件 | 可用，但偏"按钮好看" |
| designeer.xyz | 设计灵感 / 动效合集 | 灵感，非交互范式 |
| motionsites.ai/mcp · vibe-hub | 动效站点 / AI 站点聚合 | 灵感，非交互范式 |

**判断**：这 5 个能给你"看起来厉害"的视觉语言，但**给不了工具产品最要命的三件事——信息架构、操作流、状态设计**。做工具，参考对象应该是 Figma / Linear / DaVinci / 剪映 / 素材管理器这类。所以本方案里会把"视觉参考"与"交互范式"分开处理，不会拿这 5 个站推导 IA。

### R2. 这些参考隐含了"必须上 React"，与 AGENTS.md §2.2 直接冲突

`reactbits` 与 `Aceternity` 都是 React 组件。用它们 = 必须引入 React + Vite（+ Tailwind）构建链。
而 `AGENTS.md` §2.2 明确写着"**无构建步骤**：改完 F5 即可"。这是三方契约，改动须写进
`docs/spec/changelog.md` 并知会三方（§4.6）。
**这不是纯技术偏好，而是"要不要推翻一条契约"的决策，必须由用户拍板（见 §5 决策 D1）。**

### R3. 「人工审核门」是架构级改动，不是加一个页面

现状：`_runPipeline` 从第 1 步跑到第 8 步，**全程无人值守**，唯一的"停"是失败。
要支持"图片必须人工确认才继续"，至少需要：

1. 新任务状态（如 `awaiting_image_approval`）—— 现有 5 个状态里没有
2. 流水线**暂停 / 恢复**机制（现在只有 `startTask` 与 `continueTask`，语义是"从头/补跑"，不是"等人"）
3. 新 WS 事件（图片就绪待审 / 审核通过 / 驳回）
4. 审核超时与占位策略（一直不审怎么办）
5. 图片与被复用片段的一致性校验（旧任务没有图，补跑时图从哪来）

**最具体的一个坑（已实测确认）**：

> `src/pipeline.js:987 reconcileInterruptedTasks()` 的 `IN_PROGRESS = ['pending','generating','concatenating','looping','transcoding','mixing']`。
> 服务重启时，处于这些状态的任务一律被标 `failed`（有意设计，见 `AGENTS.md` §6「僵尸任务回收」）。
> **如果新状态没被显式排除，用户审核到一半、服务一次重启，所有待审任务全部变 failed。**
> 验收脚本 `verify-pipeline-fixes.js` 里对这条回收逻辑有 28 项断言，改动必须同步扩测。

### R4. 图生视频的模型能力**尚未核实**，不能假设都支持

`src/generators/dashscope.js:41` 的请求体是 `input: { prompt }` —— **没有图像入参**。
要做到"确认的图直接成为视频输入"，必须逐家核实各模型的 image-to-video 接口：

- 部分模型可能只支持文生视频 → 只能用"参考图"降级，**语义就退回方案 B**（确认的是 A 图、生成的是 B 视频）
- 各家的图生视频对图片分辨率 / 格式 / 时效有不同限制（很多是"图片 URL 有效期 24h"）

**这条必须由后端先做能力核查表，再定实现。** 不能先写代码再发现模型不支持。

### R5. 「工具」意味着状态必须活得过刷新，现在活不过

现状：任务状态在服务端（能活），但**用户正在编辑的提示词、分镜草稿、图片审核选择**都是前端内存态，F5 即丢。
工具型产品的最低要求是"关掉再开，我在做的事还在"。这需要草稿持久化（localStorage 或后端 draft 接口），
现有代码里没有。这是新增能力，不是"顺手加一下"。

### R6. 288 KB 单文件不是"换个样子"能改好的，要动 JS 结构就等于重写交互层

136 个全局函数、无模块、无类型。要拆模块，就必须重新组织调用关系与状态归属。
**因此本方案不承诺"逻辑零改动"。** 承诺的是：**业务规则不变**（质检语义、拼接校验、片段复用、循环淡化的验收口径全部保留），
但代码组织允许重写。这一点必须先说清楚，避免交付时被理解成"偷偷改了行为"。

## 5. 需要用户现在拍板的 4 个决策

### D1. 技术栈（决定整个阶段 3 的形态）

| 选项 | 含义 | 代价 | 是否要改 AGENTS.md |
|---|---|---|---|
| **A. 零构建原生模块化** | 坚持无构建，ES Module 拆文件 | 用不了 reactbits / Aceternity；动效要手写 | 不用改 |
| **B. React + Vite + Tailwind** | 可用你的全部参考库，工具生态最成熟 | 引入构建链、node_modules 显著变大、违背 §2.2 | **要改**，需 changelog + 三方知会 |
| **C. 混合** | 主工作台 React，子页保留原生 | 两套技术并存，维护成本高 | 要改 |

> 我的倾向：**B**。理由是"软件/工具"定位下，React 的组件化与状态管理是刚需，288KB 单文件正是它的反面。
> 但这**不是我能单方面定的**——它推翻的是一条三方契约。

### D2. 不支持图生视频的模型怎么办

| 选项 | 行为 |

### 7.1 用户新增的两条设计约束（2026-10-26）

1. **「前端设计要很高级，前端展示也要重点设计」** —— 与"工具不是展示"的定位存在张力，
   处理方式见 §7.2。
2. **参考资源由用户继续收集**，收集完再定视觉方向；已有 5 个参考站（ReactBits / Aceternity /
   Uiverse / designeer / motionsites+vibe-hub）继续有效。

### 7.2 「工具」与「高级」怎么共存（Lead 立场，待用户确认）

工具型产品的"高级"来自**做工**，不是**炫技**：

| 维度 | 工具型的高级 | 展示型的高级（工具里是负担） |
|---|---|---|
| 动效 | 操作反馈 <200ms、状态过渡必要且克制 | 入场动画、视差、滚动叙事 |
| 留白 | 有信息密度，不靠大留空撑气场 | 大面积留白与大图 |
| 装饰 | 几乎没有 | 渐变、光晕、粒子 |
| 字体 | 字号阶梯精确、数字用等宽/表格数字 | 大字标题当视觉主体 |

**唯一允许"展示化"的地方：成片预览区。** 那里用户是在"看作品"，值得做成影院级
（暗场、播放器质感、全屏、快捷键）。除此之外整站按工具标准做。

**对参考站的使用方式**：ReactBits / Aceternity 的动效可用，但**限定在关键位置**
（如生成中状态、审核门通过瞬间、播放器控制），不做全站铺设。

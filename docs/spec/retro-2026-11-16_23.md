# 一周返工复盘（2026-11-16 → 2026-11-23）

> 目的：不只统计「发生了什么」，而是找出**为什么同一类成本被反复支付**，并把可预防的部分
> 变成规则、自动化与流程。所有结论都尽量给到 commit / 任务 id / 实测数值；无法证实的标「未验证」。
>
> 数据来源：`git log`（198 个提交）、`app/docs/spec/changelog.md`、`app/docs/交接/*`、
> `scripts/`、`data/logs/`、实际运行脚本。统计时点：2026-11-23 15:00 前后。

---

## 1. 一句话结论

这一周不是「bug 多」，而是**三个结构性缺口**在放大成本：

1. **验证手段缺位**——UI/视觉/运行时字符串没有可自动化的验收，用户成了唯一的测试机；
2. **门禁有洞且不强制**——脚本数量涨到 109 个，注册表却只覆盖 99 个，且「注册了」不等于「参数传了」；
3. **事实源分裂**——同一份 changelog 在仓库内外各有一份、互相缺章，每个新窗口都要重新推理。

三者叠加的典型循环是：**改代码 → 自查通过 → 用户发现 → 补丁只治症状 → 再犯 → 加断言（太晚）→ 门禁没强制 → 下次还漏**。

## 3. 事故清单（按代价排序）

### 3.1 i2v 504 事故（11-19，`task_mwnosz8o_uyl4`）

- **事实**：3 段 10s i2v，首帧 1696×960 PNG 3.24 MB（dataUrl ≈4.3 MB），3 段并发；
  15:16:21Z 提交，64 秒后三段全部 `504 {}`；0 片段、任务 failed；**上游是否计费无法确认**。
- **根因**：该中转此前只验证过 5 秒 i2v；10 秒 + 3.2 MB 首帧 + 3 并发的组合从未验证；
  请求体 ≈13 MB 同时打网关，与「网关 60 秒超时」吻合。
- **修复**：首帧 >1.5 MB 压 JPEG、i2v 默认串行、502/503/504 有限重试（默认 1 次）。
- **代价延伸**：补跑成功后**又暴露两个缺陷**——success 片段 `duration` 从未写库（终检接缝/色彩永远
  「未执行」）；异步落库乱序 + 无重试，DB 停在 `mixing`（重启会被僵尸回收误判 failed）。

### 3.2 等待超时：硬编码 300s + 阈值拍脑袋（11-21）

- **事实**：`_waitForCompletion` 的 `maxWait` 硬编码 300000，唯一调用处不传参。
  任务 `task_mwp70yzl_lh54` 的 9 次成功耗时 228.3~285.1s，均值 247.7s，**最长距 300s 只剩 5%**；
  片段 #7 因此被判超时失败，用户补跑 **249.3s 成功**。
- **修复过程本身成了二次成本**：第一次把默认值定 600s（理由是「2× 观测最大值」，属拍脑袋），
  用户质疑后 4 分钟改 450，11 分钟后再改 400。
- **教训**：n=9 的紧分布（max/min=1.25）不支持「2×」这种保守系数；阈值必须有分布依据与余量说明。

### 3.3 创作页崩块：`i2vUnsupported is not defined`（11-21）

- **事实**：变量从未声明，但引用藏在 `${step === 4 && html\`...\`}` 里，**只有第 4/5 步渲染才求值**；
  静态 grep 与「只渲染第 1 步」都测不到。
- **修复**：新增 `scripts/lib-render-probe.js`，把 ESM 改写成普通脚本、用立即求值 htm 桩在 vm 里
  逐步渲染 1–5 步；删掉声明后第 4/5 步必红（负向用例）。
- **意义**：这是本周唯一一个「把不可测变可测」的修复，方向正确，但只覆盖创作页。

## 4. 共同根因（真正要修的东西）

### 4.1 R1：验证手段缺位 → 用户当测试机

**证据**：53 次「未验证」；所有 UI/视觉缺陷（黑屏、偏移、崩块、英文漏中文、设置页空白）
都是用户先发现；`verify-all` 在本沙箱因 `spawn EPERM` 跑不起来，只能逐个套件跑。

**为什么反复付钱**：每次修复都要「改 → 用户刷新 → 用户截图描述 → 再改」，
单轮成本 ≈ 1 次上下文恢复 + 1 次诊断 + 1 次补丁，而视觉问题平均要 2–3 轮。

**可预防性**：高。已证明可行的手段（本周已有雏形）：
- `lib-render-probe.js`：逐步渲染，抓「藏在分支里的未声明变量」；
- `?diag=1` 自检浮层：把布局盒模型打出来，不依赖 DevTools；
- `i18n --strict` + 数据层英文扫描。

**未解决**：CSS 布局、点击手感、真机预览仍无法自动判定；必须明确标「未验证」。

### 4.2 R2：门禁有洞 + 断言追着实现走

**证据**：
- `verify-i18n` 的 desc 写「--strict 收口」，但 `verify-all` 的 `runOne` 只按 `script:` 拉起、
  **不传参** → 该规则从未生效；
- `verify-i18n --strict` 实测长期红：`langSwitch.js` 用块注释 `/* i18n-allow */` 标记，
  而扫描器先删块注释再查标记，**把标记自己删掉了**；
- `verify-assistant.js` 一周改 29 次，两次提交叫「修过期断言」；
- 108 个脚本只有 98 个注册，9 个没有机器可读的手动理由。

**为什么反复付钱**：门禁全绿给人「已验证」的错觉；真正该拦的规则要么没传参、要么只扫了字面量。

### 4.3 R3：阈值/默认值靠猜

**证据**：300s 硬编码 + 5% 余量；600s 用「2× 最大值」；18 分钟内改 3 次。

**可预防性**：高。只要规定「改默认值必须附 n / 均值 / σ / max / 余量 / 右删失说明」，
第一次就会定在 400 附近，省掉两轮。

### 4.4 R4：静默失败与「默认放行」

**证据（同一形状重复 6+ 次）**：`readyState<2` 裸 return、`duration` 不落库、
中间态当终态、写库失败只打日志、`skipped` 被当 `passed`（历史红线）、
单片段拼接写死 `passed:true`（历史）。

**共同机制**：函数用「什么都不返回」表达「没跑到」，而下游把「没有失败」当「成功」。
这是**数据形状问题**，不是某个人不小心。

### 4.5 R5：事实源分裂（本周最贵、也最容易被忽略）

**实测**：`app/docs/spec/changelog.md`（262 KB，git 受控）与根 `docs/spec/changelog.md`（227 KB，git 外）
**互相缺章**：

- 根版多出：11-03 验收脚本自清理、11-08/11-09 图片生成、11-09 前端单版本收口、
  11-09 交接断点、11-10 Base URL、11-11 失败原因可诊断、**11-23 日间/夜间双主题**（8 节）；
- 受控版多出：11-16 小智多条线、11-19 深夜两个落库缺陷、E11–E15、11-23 出图调色（12 节）。

**为什么反复付钱**：每个新窗口只会读到其中一份 → 重复踩已知坑（红线 15 记过同样的事故，
11-12 已经写过「必须改成指针文件」，**一周后仍分叉且更长**）。规则写了没执行，等于没写。

### 4.6 R6：上下文切换税

**证据**：84 个 docs 提交（42%）、47+ 份交接、方案文档单日改 16 次、changelog 改 19 次。

**机制**：上下文快满 → 写交接 → 新窗口重读 → 重新推理 → 再写交接。
其中一部分是必要的（长任务必须交接），但当「事实源分裂 + 门禁不可信」时，
交接成本会翻倍，因为接手者无法相信任何一份文档。

## 5. 成本模型：为什么每次都要再付一遍

把单次事故拆成阶段，可以看到钱花在哪：

| 阶段 | 典型耗时 | 能否自动化 |
|---|---|---|
| 用户发现并描述（截图/口述） | 数分钟~数小时 | 否（但可减少发生次数） |
| 诊断（读日志/复现/查 changelog） | 10–40 分钟 | **部分**：服务版本、门禁状态可一键 |
| 修复（含试错） | 10–60 分钟 | 否 |
| 误判（旧进程/缺探针导致「修了没用」） | **整轮返工** | **是**：`check-server-version` 一条命令 |
| 补断言（往往事后才补） | 20–60 分钟 | 部分（探针/扫描器可复用） |
| 交接（写文档、下个窗口重读） | 30–90 分钟 | 部分（单一事实源可省一半） |

**结论**：最贵的不是写代码，是「诊断 + 误判 + 交接」。这三项恰好最适合自动化。

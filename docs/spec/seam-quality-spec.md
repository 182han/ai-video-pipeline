## 1. 为什么「不自然」至今没有被测量（代码证据）

| 质检项 | 位置 | 它实际测什么 | 是否读画面 |
|---|---|---|---|
| `checkConcat` | `src/qualityChecker.js:319` | 产物时长 ≈ 各输入时长之和（防 `-c copy` 静默截断）、完整解码 | **否**（只测时长/解码） |
| `checkLoop` | `src/qualityChecker.js`（循环质检） | 成片**末尾 vs 开头**的 SSIM（首尾能否无缝循环） | 是，但只测**一处**：整片首尾 |
| 其余 9 项 | 片段黑帧/模糊/重复/时长、提示词、分镜、NSFW、终检等 | 各自对象 | 与「片段之间的缝」无关 |

**结论（已核实）**：`_concat.mp4` 内部每两道缝（N 个片段 → N−1 道缝）**没有任何检测覆盖**。
AGENTS.md §6 记录过一次「接缝相邻帧 SSIM 0.238」，但那是一次性人工排查的结论，
**没有落成检测项**，所以后续每次拼接都不会被拦住。

## 2. 指标定义（含「为什么用这个度量」）

全部度量由 ffmpeg 原生滤镜算出，**不引入任何新依赖**（AGENTS.md §4.6）。

### 2.1 五个指标

| # | 指标 | 计算方式 | 单位/范围 | 回答什么问题 |
|---|---|---|---|---|
| 1 | **ΔE76**（均色差） | 缝两侧代表帧各自取 `signalstats` 的 YAVG/UAVG/VAVG → YUV→RGB(BT.709, TV range) → XYZ(D65) → CIELAB → 欧氏距离 | 0~100+，>2.3 肉眼可辨 | **整体色调**是否跳变 |
| 2 | **ΔY / 峰值Y极差** | 两帧 YAVG 之差；窗口内逐帧 YAVG 的极差 | 0~219 | **整体亮度**是否跳变 |
| 3 | **min SSIM + 低谷宽度** | 两路同源错位一帧 → `ssim` 滤镜逐帧对输出 | 0~1 | 结构是否**断崖**（硬切）；低谷宽度 ≤2 = 断崖，≥3 = 多帧混合 |
| 4 | **MAD**（像素级平均绝对差） | 两路对齐后 `blend=all_mode=difference` + `signalstats` → YAVG | 0~255 | 逐像素变化量；**同时反映景物不同与局部明暗**；相对同段基线得「MAD 倍数」 |
| 5 | **SE**（接缝视觉能量） | `dSSIM_i = 1 − SSIM_i`；`baseline = median(dSSIM)`；`SE = Σ max(0, dSSIM_i − baseline)` | 0~∞ | 把「接缝自身造成的结构变化」从「画面自然运动」里剥出来；**唯一能横向比较硬切与叠化的指标** |

### 2.2 为什么必须要 MAD，不能只看「平均亮度差」

「两帧平均亮度之差 ≈ 0」**不等于**「亮度没跳变」：
一片星空与一片森林的平均 luma 可以都等于 40，但逐像素差异巨大。
早期版本只做了 ΔY，硬切缝全部读成 `ΔY≈0.1`（假阴性）。
加入 MAD 后同一批缝读到 **MAD 33~93（自然运动的 10~51 倍）**。

**同时要纠正一处历史口径**：`src/processors/transitionMixer.js:8` 记录的
「逐帧亮度差 46.5」其实是**像素级 MAD 类指标**，它同时混入了「景物不同」与「明暗不同」。
本规格把两者拆开：`ΔY` 才是「整体亮度跳变」，`MAD` 是「像素级总变化」。

### 2.3 为什么 ΔE76 而非 RGB 欧氏距离

RGB 距离与视觉感知不成线性（例如同样 30 的距离，在暗部比亮部明显得多）。
ΔE76 走 CIE Lab，与人眼感知更接近，且 >2.3 是行业通用「刚可察觉」阈值。
脚本**两者都输出**：ΔE76 用于判定，ΔRGB 仅作对照。

> 精度边界（诚实标注）：YUV→RGB 按 BT.709 + TV range 换算。若源是 BT.601 或 full range，
> 绝对色值会有整体偏移，但**同一视频内偏移一致**，做缝两侧**差值**时相互抵消，
> 不影响接缝判定。这是推断，未逐条验证色彩空间。

### 3.2 缝位置怎么来的

1. 显式 `--seams`；
2. 否则从 `data/tasks/<taskId>.json` 取各片段 `duration`，累加；
   **若拼接步骤留痕显示真的做了转场**（`steps.concatenation.qcDetails.transition.transitions > 0`），
   第 i 道缝位置要前移 `(i+1) × fadeDuration`（每道缝吃掉一个淡化时长）。
   该公式与 `transitionMixer.js:16` 的「成片时长 = Σd_i − (N−1)·F」一致，
   实测验证：`task_mvhlxnm7_1mch` 7 段 Σ=45.13、F=0.4 → 预测 42.73，ffprobe 实测 **42.767**（差 0.034s）。
3. 否则回退 `scdet` 场景检测（score ≥ 10 或 mafd 显著高于中位数的局部峰）。

> 踩过的两个坑（已修，写在这里防止回退）：
> - `-ss` 之后 ffmpeg 输出的 `pts_time` 从 0 重新开始，拿它跟接缝绝对时间比会永远挑到窗口最后一帧 → **必须加回 seek 起点**；
> - 所有「两侧对比」必须用**最不相似那一帧对**的下标（pair 下标），用「最接近缝时间的帧」会错开一帧，硬切时 MAD 恰好读成自然水平。

### 3.3 判定「硬切 vs 淡化」的规则（可判据，不靠观感）

| 判型 | 条件 |
|---|---|
| `hardcut` | min SSIM < 0.75 **且** 低谷宽度 ≤ 2 **且** 断崖落差 > 0.15 |
| `dissolve` | 低谷宽度 ≥ 3（连续多帧低于 0.75，典型的混合区） |
| `continuous` | min SSIM ≥ 0.75（缝处几乎无变化：要么真无缝，要么缝位置偏了） |
| `undetermined` | 抽帧/统计失败 → **按 §4.1 语义视为「不通过」，不得当通过** |

## 5. 回答：现有成片的「不自然」主要属于哪一类？

### 5.1 结论

> **主要是「内容跳变」（第三类）。色调跳变与亮度跳变是硬切场景下的伴生现象，不是独立的、值得单独去修的病因。**

三态：**不通过**（现有成片确实不自然，有 15 道缝的实测数值支撑）。

### 5.2 为什么这个结论站得住（三条互相独立的证据）

1. **反证法（最强）**：`task_mvhlxnm7_1mch` 已经开了 0.4s 真淡化，6 道缝的
   ΔE76 ≤ 0.42、\|ΔY\| ≤ 0.39 —— 色调与亮度**已经几乎没有差别**。
   如果病因是调色/亮度，这条成片用户应该满意。但用户仍说「不自然」。
   → **色调/亮度不是瓶颈。**
2. **MAD 倍数仍然很高**：同一批转场缝的 MAD 是自然运动的 **1.8~7.0 倍**，
   且影片条里能看到**双重曝光鬼影**（两个不相干场景叠在一起）。
   → 转场只是把「跳变」摊薄成「模糊的叠化」，**语义不连续这件事没变**。
3. **正对照**：`task_mvglbfkw_w5vg` 的缝 #1 是**硬切**，但两段画面几乎相同
   （ΔE76 0.21、SSIM 0.908）—— 用户不会有感。
   → **决定观感的是镜头之间是否语义连续，而不是接缝用了什么技术。**

### 5.3 对「三种病因」框架的修正建议

| 原假设 | 实测修正 |
|---|---|
| 色调跳变可修（调色匹配） | 在硬切组确实存在（ΔE76 最高 48），但**它是「镜头不同」的结果而非原因**；在已开转场的成片里 ΔE76 ≈ 0.1，已无优化空间 |
| 亮度跳变可修（亮度归一化） | 同上。硬切组 `task_mvhrynuu_ehtn` 缝 #4 有 **ΔY −90.74**（画面骤然变暗），这是真实缺陷、值得单独修；但只修它不会让成片「自然」 |
| 内容跳变只能重生成 | **优先级最高的其实是「相邻镜头的语义连续性」**（同场景延续 / 景别递进 / 色彩与运动朝向呼应），这是提示词与分镜层的责任，不是拼接层的 |

## 6. 阈值建议（第一版，基于本批实测校准）

| 指标 | 通过 | 警告 | 不通过 | 校准依据 |
|---|---|---|---|---|
| min SSIM | ≥ 0.90 | 0.75 ~ 0.90 | < 0.75 | 转场组全部 0.83~0.95、硬切组全部 0.42~0.54，两群无重叠；0.75 落在空档 |
| ΔE76 | < 10 | 10 ~ 25 | ≥ 25 | 转场组最大 0.42；硬切组多有 27~48。取 10 留足余量（>2.3 才「可辨」，但接缝容许比单帧更宽） |
| \|ΔY\| | < 12 | 12 ~ 30 | ≥ 30 | 转场组 ≤ 0.39；硬切组多 14~90 |
| MAD 倍数 | < 2.5 | 2.5 ~ 8 | ≥ 8 | 转场组 1.8~7.0（鬼影）；硬切组 9.8~51.9 |
| SE | < 0.6 | 0.6 ~ 1.0 | ≥ 1.0 | 转场组 0.31~1.01、硬切组 0.67~1.59；重叠较多，**只作辅助，不单独判 fail** |

> **阈值必须可配置**（`.env`），且带版本号 —— 参照现有 `QC_LOOP_SSIM_THRESHOLD` 与
> `qcVersion` 机制（AGENTS.md §6「质检可信度暴露到 API」）。
> 建议：`QC_SEAM_SSIM_MIN=0.75`、`QC_SEAM_DE76_MAX=10`、`QC_SEAM_DY_MAX=12`、`QC_SEAM_MAD_RATIO_MAX=8`。
> 阈值一旦调整，`qcVersion` 必须升版，否则历史任务的可信度标注会误导（既有机制，勿绕过）。

## 7. 接入 `qualityChecker` 的方案（本期不实施）

### 7.1 硬约束（摘自 AGENTS.md，实现时必须逐条满足）

| 约束 | 出处 | 对本检测的含义 |
|---|---|---|
| `skipped` ≠ `passed` | §4.1 | 抽帧失败、ffmpeg 出错、探测不到时长 → **一律 `passed:false`**，不许给 `skipped` |
| 只有业务上本就不适用才允许 `legitimateSkip` | §4.1 | 「只有 1 个片段」= 没有缝 = **合法跳过**（并写明 `legitimateSkip:true, reason:'单片段无接缝'`）；其他任何情况都不许跳过 |
| 禁止随机数冒充结论 | §4.2 | 所有数值必须来自 ffmpeg 实测 |
| 不许把退出码 0 当成功 | §4.3 | 必须校验 fs 产物 + 数值范围；解析空 = undetermined = 不通过 |
| `qualityChecker.js` **禁止整文件覆盖写** | §4.5 | 只能增量 `edit`，在新小节里加 `checkSeam()`，**不得 `write` 整个文件** |
| 三态结论 | §5.1 | 返回值必须能区分 通过/不通过/**未验证** |

### 7.2 建议的检测项设计

```
QC_ITEMS 追加一项：{ key: 'seam', name: '片段接缝质量', ... }
```

**签名**（与现有 `checkConcat`/`checkLoop` 风格一致）：

```js
// 只在「拼接产物 + 已知片段时长」都具备时才能测
// 返回 { passed, level, undetermined?, legitimateSkip?, details:{seams:[...], summary:{...}} }
async checkSeam(concatPath, clipDurations, options = {})
```

**判定逻辑（逐缝）**：
1. 对每道缝取 ±0.8s 窗口（若下方片段数很多，可只抽前 12 道缝 + 随机 N 道 —— 但**随机只能用于抽样位置，不能用于结论**，§4.2）；
2. 算 min SSIM / ΔE76 / ΔY / MAD 倍数 / SE；
3. 任一缝不通过 → 整体 `passed:false`，`level:'fail'`，并在 `details.seams` 里逐缝给出原因字符串（参照现有「片段缺失：应有 N 个，实际 M 个」的写法）；
4. 有缝 `undetermined` → **整体 `passed:false` 且 `undetermined:true`**（不可判定 ≠ 通过，§4.3 同理）。

**汇总口径必须与现有 `checkClip`/`checkFinal` 一致**：
`failedItems` 与 `notRunItems` 都为空才 `passed`。
**不要**写 `passed || skipped`（§4.1 明确禁止复制该写法）。

### 7.3 接入点（三处，按风险从低到高）

> **实际落地（2026-10-27）**：采用接入点 **B（终检）**，而不是原推荐的 A。
> 原因：`checkFinal` 的 `results` 汇总会真正影响 `totalPassed`（A 只是记录、不阻断），
> 而"质检项"应当能判不通过；且三处 `checkFinal` 共用 `pipeline._finalQcOptions()`，
> 一处改动即可全覆盖，不需要在 3 条拼接路径里各插一次。
> 缝位置由 `pipeline._seamQcOptions()` 生成：用 `steps.concatenation.qcDetails.transition`
> 的**实际留痕**算 fade（补跑历史产物时当前配置可能已变），Mock 素材走合法跳过。

| 接入点 | 位置 | 风险 | 说明 |
|---|---|---|---|
| A. 拼接步骤质检 | `pipeline.js` 调用 `checkConcat` 处 | **低**（只多一个检测项，不改流程） | 与 `checkConcat` 并列调用，结果并入 `steps.concatenation.qcDetails`；但**不阻断**流程 |
| **B. 终检（已采用）** | `checkFinal` | 中 | 终检已读画面（NSFW），抽帧能力可复用；缝位置从任务记录传入；结论参与 `totalPassed` |
| C. 自动重拼 | pipeline 捕获 seam fail 后自动开转场重拼一次 | **高** | 会二次编码、耗时翻倍；且「自动改参数」属于产品决策，**本期不做** |

**性能预算（实测，非估算）**：每道缝约 **2.3s**（6 道缝实测 14.1s，720p）。
默认 `QC_SEAM_MAX_SEAMS=8`（约 18s）；超过则均匀抽样，并在
`details.summary.sampled / unscanned / partialCoverage` 标注，**且把
「本次仅检测 N/M 道缝（均匀抽样），未检测的 X 道不计入结论」写进 `reason`（通过与不通过都写）**
—— 覆盖面必须对用户可见，不能让"没测的部分"靠沉默变成通过（§4.1 同构要求）。
可优化（未做）：把「两帧各 1 次 signalstats + 1 次 blend-difference」合成单次 ffmpeg
（需 `split` 分支），预计省 ~30%。

### 7.4 与 `checkConcat` 的分工（避免重复/漏测）

| | `checkConcat`（已有） | `checkSeam`（新增） |
|---|---|---|
| 防截断 | ✅ 时长 ≈ Σ片段 | ❌ 不重复 |
| 完整解码 | ✅ | ❌ |
| 接缝是否自然 | ❌ | ✅ |
| 单片段任务 | 走「只有 1 个成功片段」分支 | `legitimateSkip:true`（无接缝） |

## 9. 转场默认值：性能实测数据（回答「30 分钟开 xfade 要多久」）

### 9.1 实测（`bench-seam-perf.js --task task_mvhrynuu_ehtn --fade 0.4`）

样本：真实任务的 7 个片段（6+6+7+7+7+7+7 = 47.00s 输入，成片 44.60s），1280×720@30。

| 方案 | 实测耗时 | 换算吞吐 | 产物时长 |
|---|---|---|---|
| A) `-c copy` 直拼 | **0.46 s** | 102.0 秒成片/秒墙钟 | 47.00s |
| B) 整片重编码直拼（`-preset medium -crf 23`） | **8.13 s** | 5.78 秒成片/秒墙钟 | 47.00s |
| C) 生产代码真转场（`transitionMixer`，6 道 0.4s fade） | **11.36 s** | 4.14 秒成片/秒墙钟 | 44.60s（期望 44.60，实测一致） |

派生比值（同一台机器、同一批输入）：
- **重编码直拼 / copy 直拼 = 17.6×** ← 成本跃升主要发生在这里
- **转场 / 重编码直拼 = 1.40×** ← 转场本身只多 40%
- 本次 `归一化片段数 = 0`（片段规格已统一），即**只编码了一遍**。
  若片段分辨率/帧率/pix_fmt 不一致，`transitionMixer.js:291-326` 会先**逐段重编码**
  （veryfast crf18）再整片编码（medium crf23）→ 最坏情况约 **2 倍**编码量（代码推断，未实测该场景）。

### 9.2 30 分钟成片推算（基于上面**实测吞吐**，非拍脑袋）

| 方案 | 推算耗时 | 依据 |
|---|---|---|
| copy 直拼 | 1800 ÷ 102.0 ≈ **0.3 分钟** | A 的实测吞吐 |
| 整片重编码直拼 | 1800 ÷ 5.78 ≈ **5.2 分钟** | B 的实测吞吐 |
| 整片 xfade 转场 | 1800 ÷ 4.14 ≈ **7.3 分钟** | C 的实测吞吐 |
| 片段需归一化时（最坏） | 约 **12~14 分钟** | 2 倍编码量（代码推断） |

> **结论（三态：已核实）**：所谓「长片会明显变慢」，真实幅度是
> **5.2 分钟 → 7.3 分钟（+2.1 分钟）**，不是数量级恶化。
> 真正昂贵的是「不再 `-c copy`」（0.3 → 5.2 分钟）。转场只是压在这之上的 40%。

### 9.3 「只对缝附近处理」是否可行（按段切分 → 逐缝 xfade → 再拼）

**可行性（推断）**：可行但有一个硬前提 —— 未重编码的中间段与重编码的缝段
**编码参数必须完全一致**（codec/profile/level/pix_fmt/timebase/GOP 对齐），
否则 `-c copy` 再拼接会失败或花屏。现有片段由不同模型生成，参数并不天然一致。

**成本结构（用同一批实测吞吐推算）**：

| 路径 | 公式 | 30 分钟 / 60 道缝的推算 |
|---|---|---|
| 整片 xfade | 全片时长 ÷ 4.14 | ≈ 7.3 分钟 |
| 只处理缝 | 缝总秒数（60×0.8=48s）÷ 4.14 + 其余 1752s ÷ 102 | ≈ 0.2 + 0.3 ≈ **0.5 分钟** |

即理论上有 **~15 倍**收益。但代价：
1. 需要先把所有片段归一化到同一编码参数（这一步本身就是一次全量重编码，
   **会吃掉大部分收益** —— 除非片段从一开始就用统一参数生成）；
2. 拼接点从「1 次」变成「N+1 次 copy 拼接」，每个接缝都要额外校验时长与解码（§4.3 同理）；
3. 实现复杂度显著高于「整片 xfade」。

**建议**：**短期不要做逐缝方案**。先把转场默认打开（+2 分钟/30 分钟），
把「片段统一编码参数」作为生成层的长期改进项，再回头看是否需要逐缝处理。

### 9.4 对「转场默认值」的建议（需产品拍板）

| 选项 | 说明 | 研发倾向 |
|---|---|---|
| 保持 `TRANSITION_ENABLED=false` | 现状零回归 | ❌ 本次实测已证明它就是「不自然」的主要来源之一（5/6 真实成片是硬切） |
| **改为默认 true（fade 0.4s）** | 30 分钟多花约 2 分钟；接缝 SSIM 从 0.42~0.54 提升到 0.83~0.95 | ✅ 推荐 |
| 默认 true 但仅 `daily/final` 档 | `quick` 档仍走 copy 直拼，保留快速预览体验（此时拼接不参与交付） | ✅ 可叠加 |
| 自动检测→必要时才开 | 先 copy 直拼 + 测缝，坏才重拼 | ⚠️ 会二次编码（最坏 0.3+7.3 分钟），且「自动改参数」需产品同意 |

> 注意：**打开转场会改变成片时长**（Σd − (N−1)×F）。
> `checkConcat` 必须传 `expectedDuration`，否则会把正确产物误判成「拼接被截断」
> （AGENTS.md §6 已记录该坑）。

# 交付与后续同步说明

> 面向：交付双方（交付方 = 本仓库维护者，接收方 = 部署/二次开发团队）。
> 目的：把「代码怎么给、以后怎么同步、哪些东西不跟着代码走」一次说清，避免交付后各改各的。

---

## 一、仓库里有什么、没有什么

| 在仓库里（跟着 git 走） | 不在仓库里（各自维护） |
|---|---|
| 后端 `src/`、入口 `server.js`、`config.js` | `.env`（含所有 Key 与数据库密码） |
| 前端 `web/`（React UMD + htm，零构建） | `node_modules/`（依赖，需要自己装） |
| 全部验收脚本 `scripts/verify-*.js` + `doctor.js` | `tools/ffmpeg/`（约 640 MB 二进制） |
| 文档 `docs/`、`AGENTS.md`、`Dockerfile` | `output/`、`clips/`（成片与片段，运行时产物） |
| `package.json` + `pnpm-lock.yaml` | `data/`（任务 JSON、日志、缓存、用户表） |
| `assets/bgm/manifest.json`（配乐清单） | `assets/bgm/*.mp3`（音频文件，需自备并注意版权） |

**结论**：代码同步 ≠ 环境同步。`.env`、数据库、素材、产物都不会跟着 `git pull` 过来。

---

## 二、原则：只有一个"上游"

交付时**必须**明确哪一个是唯一上游（single source of truth），否则一定会出现"两边各推一版、历史分叉"。

### 方案 A（推荐）：以接收方仓库为上游

1. 接收方提供仓库地址；
2. 交付方把本地 `main` 推上去（`git push <对方地址> main`）；
3. 之后交付方的每次更新：`git push <对方地址> main`；
4. 接收方部署前：`git pull` → 重启服务。

**优点**：历史只有一条，`git log` 能一路追到第一行代码；回滚只需 `git checkout <tag>`。

### 方案 B：以交付方仓库为上游

接收方 `fork`/`clone` 只读跟随，交付方推自己的仓库，接收方定期 `git pull upstream main`。

**缺点**：接收方如果也在改代码，容易和上游冲突，需要走 PR 流程。

### 反例（不要这样做）

把代码打成 zip 发过去、对方新建一个仓库提交一次。这样两边是**两条没有共同祖先的历史**，之后既不能 `pull` 也不能 `push`，只能手工打补丁。

## 三、分支与版本约定

| 约定 | 说明 |
|---|---|
| `main` | 永远是**能部署的稳定版**，随时可以拉起服务 |
| `tag` | 每次交付打 tag：`v1.0.0`、`v1.1.0`…；接收方部署记录当前 tag |
| 日常改动 | 交付方在自己分支开发，验证通过再合进 `main` |
| 接收方改动 | 若接收方也要改代码：从 `main` 开分支 → 合回自己的上游；**不要直接改 `main`**，否则下次同步会冲突 |

**回滚**（部署出问题时）：

```bash
git checkout v1.0.0     # 切回上一个交付版本
node scripts/doctor.js  # 自检
# 重启服务
```

## 四、同步动作清单（每次更新都照这个走）

**交付方**

```bash
cd app
git status --short                 # 确认没有别人的未提交改动混进来
node scripts/verify-all.js --fast  # 至少跑快速组；本机 spawn EPERM 时逐个跑
git add -A && git commit -m "..."  # 一次提交只做一件事
git tag v1.x.0
git push <上游> main --tags
```

**接收方**

```bash
git pull                # 或 git fetch && git merge
pnpm install --frozen-lockfile    # lockfile 有变化时才需要
node scripts/doctor.js            # 0 个 ERROR 再往下
# 重启服务（先停旧进程，再起新进程；不要两个实例并行）
```

---

## 五、必须知道的三个副作用

1. **重启 = 全员登出**：会话存在进程内存里，没有持久化。重启后所有人需要重新登录。
2. **重启 = 运行中任务中断**：生成中的任务会被启动时的回收逻辑标记为 `failed`（不会冒充成功），可在页面上「补跑」。
3. **升级要在维护窗口做**：不要在有任务跑的时候重启。

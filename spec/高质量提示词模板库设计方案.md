# 高质量提示词模板库设计方案（第三批实施）

> 本 spec 自包含，研发可直接按 §3-§7 执行。所有路径基于 `app/` 现有代码结构。
> 前置：指令 A（themeSelect 动态化）+ 指令 B（LLM 真分镜，§9.1）已完成。

---

## 0. 结论先行

**问题不是"缺模板"，是现有模板"只有词、没有结构"。**

现有 9 个模板每个只有 8 个通用风格词（`cinematic lighting` / `4K ultra HD` / `highly detailed` ...）。行业共识是这类空泛赞美词**给不了模型任何可锚定的东西**——这正是生成质量上不去的根因。

本方案把模板从"词表"升级为"结构化模板"，依据两条权威来源：

1. **可灵官方公式**（P0 级）
   ```
   Prompt = Subject(主体) + Subject Movement(主体运动) + Scene(场景)
            + ( Camera Language(镜头语言) + Lighting(光影) + Atmosphere(氛围) )
   ```
2. **`jnMetaCode/ai-shortfilm-prompts` 的 5 段结构**（MIT 协议，可商用）
   ```
   1. Core theme          ← 3-6 个风格标签，用 | 分隔
   2. Character & scene   ← 主体/环境细节
   3. Atmosphere & quality← 视觉基底 / 色调 / 风格内核
   4. Camera rules        ← 单镜或多镜 / 机位 / "呼吸感"浮动
   5. Storyboard          ← 逐秒 或 逐镜 拆解
   ```

**三条反直觉规则**（对风光片尤其有效，必须写进模板设计）：

1. **写真实相机+镜头型号**——不写 `cinematic feel`，写 `simulated IMAX film camera + Panavision C-series lens, 35mm focal, f/4 aperture`。AI 训练数据把具体型号绑定到真实电影美学。
2. **描述瑕疵**——完美感 = 假。真实的质感来自细节。
3. **结尾留白**——`No people. No vehicles. Just the landscape holding still as light shifts.`

## 2. 目标结构（向后兼容）

**核心原则：新增 `structure` 字段，保留 `styleEnhancers` 与 `negative` 不动。**

原因：`styleEnhancers` 被前端模板管理页、`getThemes()`、旧 `optimizeWithTemplate` 依赖；用户通过 UI 自建的模板只有 `styleEnhancers`，必须能降级运行。

```js
{
  name: '海洋',
  emoji: '🌊',
  keywords: [...],              // 保留：行级标签路由用
  negative: 'people, boats, text, logos',   // 保留
  styleEnhancers: [...],        // 保留：向后兼容 + 无 structure 时的降级
  structure: {                  // 新增：结构化字段
    subjectPool: [],            // 景观主体池（场景层）
    movementPool: [],           // 主体运动池（5-15s 内可见的运动）
    cameraPool: [],             // 运镜池（含真实机型/镜头型号）
    lightingPool: [],           // 光影池
    atmospherePool: [],         // 氛围池
    quality: [],                // 质感/画质（固定拼接，非随机）
    endingPool: []              // 结尾留白池
  }
}
```

## 4. 组合逻辑改造（`optimizeWithTemplate`）

**改造目标**：从"随机拼词"改为"按公式结构化组合"。

### 4.1 新组合公式

```
最终提示词 = 用户原句（保留）
           + 运镜(cameraPool 取1)
           + 光影(lightingPool 取1)
           + 氛围(atmospherePool 取1)
           + 质感(quality 全量拼接)
           + 结尾(endingPool 取1，句号分隔)
```

即：`${userPrompt}, ${camera}, ${lighting}, ${atmosphere}, ${quality}. ${ending}`

### 4.2 关键要求

1. **用户原句必须保留**——模板只做"增强"，不改写用户意图（与指令 B 的多提示词模式一致）
2. **同主题多片段必须差异化**——用 `options.seed`（传 `clip.index`）做**确定性选择**，避免相邻片段提示词雷同（与 `qualityChecker` 的相邻重复检测形成双保险）
3. **长度控制**——拼接后若超过 **2400 字符**则截断（可灵上限 2500，留 100 余量；其他模型上限不同，见 §7）
4. **向后兼容降级**——模板无 `structure` 字段时（用户 UI 自建模板），回退现有 `styleEnhancers` 随机拼接逻辑

### 4.3 伪代码

```js
optimizeWithTemplate(userPrompt, theme = 'landscape', options = {}) {
  const template = this.templates[theme] || this.templates.landscape;
  const s = template.structure;

  // 降级：无 structure（UI 自建模板）→ 旧逻辑
  if (!s) return this._legacyTemplateOptimize(userPrompt, template);

  const seed = Number.isFinite(options.seed) ? options.seed : 0;
  const pick = (pool, offset) => (pool && pool.length)
    ? pool[(seed + offset) % pool.length] : '';

  const parts = [
    userPrompt,
    pick(s.cameraPool, 0),
    pick(s.lightingPool, 1),
    pick(s.atmospherePool, 2),
    (s.quality || []).join(', ')
  ].filter(Boolean);

  let optimized = parts.join(', ');
  const ending = pick(s.endingPool, 3);
  if (ending) optimized += `. ${ending}`;
  if (optimized.length > 2400) optimized = optimized.slice(0, 2400);

  return {
    method: 'template',
    theme: template.name,
    original: userPrompt,
    optimized,
    negative: template.negative
  };
}
```

### 4.4 调用方改造

- `pipeline.js` 第 1-2 步逐片段优化时，把 `clip.index` 作为 `seed` 传入（当前调用在 `pipeline.js:229-241`）
- `optimizeWithAI` 的 systemPrompt 需同步注入结构化参考（当前 `promptOptimizer.js:434-441`），让 LLM 也按公式输出

### 4.5 ⚠️ 单提示词模式的覆盖冲突（新增，必改）

**背景（指令 B 完成后新暴露的集成缺口）**：单提示词模式的当前流程存在"步骤1白做"的问题：

```
步骤1  prompt_optimize：optimizeWithTemplate(task.prompt) → clips[i].prompt = "优化结果 - scene N"
步骤2  storyboard：llmService.storyboard(...) 有 Key 时 → 覆盖 clips[i].prompt = LLM 场景
```

**后果**：
1. 步骤1 的模板优化在单提示词模式被步骤2 **完全覆盖**，白做
2. LLM 生成的场景**未经模板结构化**，`structure` 各词池（运镜/光影/氛围/结尾）根本没作用到最终提示词
3. `llmService.enhancePrompt`（§9.1 增强链）**无任何调用点**，是死代码

**修复方案（二选一，推荐 A）**：

- **方案 A（推荐）**：步骤2 LLM 分镜后，对每个生成场景**再套一次模板结构化**——
  ```js
  // pipeline.js 步骤2，scenes 写回前
  for (const s of scenes) {
    const structured = promptOptimizer.optimizeWithTemplate(s.prompt, task.theme, { seed: s.index });
    taskManager.updateClip(taskId, s.index, { prompt: structured.optimized });
  }
  ```
  效果：**LLM 负责"差异化场景内容"，模板负责"专业运镜/光影/氛围结构"**，两者互补不冲突。

- **方案 B**：改用 `llmService.enhancePrompt(scene, theme)` 替代模板结构化（每段多一次 LLM 调用，成本翻倍，不推荐）

**多提示词模式不受影响**（步骤2 本就跳过覆盖，§10B）。**无 Key 降级时不受影响**（步骤1 结果保留）。

**新增验收项**：
- [ ] 单提示词 + 有 LLM Key：最终 `clips[i].prompt` 同时含 **LLM 差异化场景** 与 **模板运镜/光影/结尾**（非纯 LLM 裸输出）
- [ ] `enhancePrompt` 若保留则必须有调用点，否则删除（不留死代码）

## 5. 负面词接入可灵（修复 P4）

### 5.1 现状
`kling.js:78-84` 的请求 body 只有 `model_name/prompt/duration/mode/aspect_ratio`，**没有 negative 字段**——模板里的 `negative` 从未生效。

### 5.2 改造
在 `kling.js` `_createTask` 的 body 中增加负面词字段。

⚠️ **研发必须先核实可灵官方字段名**（`negative_prompt` 或其他），以官方文档为准，**不得凭猜测填写**。核实步骤：
1. 查可灵开放平台文档 `POST /v1/videos/text2video` 的请求参数表
2. 确认字段名、是否必填、长度上限
3. 若官方不支持该字段 → 放弃此改造，改为在提示词末尾用描述性语句规避（不写 `no X`，写"画面中只有 X"）

### 5.3 其他模型
`seedance.js`/`agnes.js`/`siliconflow.js` 同理核实；不支持的跳过。

## 6. 前端适配

1. **模板管理页**：模板卡片增加"结构化字段"展示（主体池/运镜池/光影池的数量），只读即可
2. **模板编辑弹窗**：`structure` 字段可选编辑（保持 JSON 文本域方式，避免复杂 UI）；用户不填则走降级逻辑
3. **保持极简白底风格**，不引入新 UI 框架
4. **创建页主题下拉框**：本方案不新增模板，仅升级内容——与指令 A 的动态化兼容，无需额外改动

## 7. 模型提示词长度上限（研发需注意）

| 模型 | 提示词上限 | 处理 |
|------|-----------|------|
| 可灵 Kling 3.0 | 2500 字符（`kling.js:80` 已截断） | 本方案统一按 2400 截断 |
| 其他模型 | 需逐一核实 | 在各自适配器内按实际上限截断 |

**风险**：结构化提示词会变长，截断会丢失"结尾留白"部分——所以 `quality` 拼接在前、`ending` 放最后，被截断时优先牺牲结尾（可接受）。
